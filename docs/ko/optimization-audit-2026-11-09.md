## A01. ID가 없는 메시지에서 차분 비교 실패

관련: [nodeStorage.ts](../../src/ts/storage/nodeStorage.ts) 1507행,
[database.svelte.ts](../../src/ts/storage/database.svelte.ts) 2275~2285행,
[chatDeltaSync.ts](../../src/ts/storage/chatDeltaSync.ts) 70~85행,
[chatFingerprint.ts](../../src/ts/storage/chatFingerprint.ts).

받은 메시지에 `chatId`가 없으면 `normalizeChat()`이 임의 UUID를 추가합니다.
이후 클라이언트는 보정된 메시지로 fingerprint를 계산합니다. 서버는 메시지 ID를 보정하지
않은 원본과 비교하므로 같은 대화라도 불일치합니다. 레거시·가져오기·일부 플러그인이 만든
메시지가 해당할 수 있으며, 이미 안정적인 메시지 ID가 있는 대화에는 해당하지 않습니다.

실제 정규화 함수와 서버 fingerprint 함수로 확인한 결과:

```text
firstClientPrefixMatchesServer: false
secondClientPrefixMatchesServer: false
sameUnchangedServerProducesSameClientIDs: false
afterPersistingIDsPrefixMatches: true
```

정상 저장으로 ID가 서버에도 반영되기 전까지 반복될 수 있습니다. 기존 호환성 테스트는
raw 서버 응답으로 비교값을 만들어 실제 클라이언트 정규화 차이를 놓칩니다.

수정 방향: 서버가 응답 전에 누락된 메시지 ID를 한 번 보정·영속화하거나, UI 정규화 전의
원본을 비교 기준으로 따로 보관합니다. fingerprint에서 ID를 단순 제외하면 북마크·편집 감지의
메시지 정체성과 충돌할 수 있습니다. 실제 NodeStorage 경로를 통과하는 회귀 검사가 필요합니다.

## A02~A04. 캐시 오류 처리와 삭제 정리

### A02 — 읽은 사본을 최근 사용 시각 갱신 실패 때문에 버림

[chatCopyStore.ts](../../src/ts/storage/chatCopyStore.ts) 80~100행은 조회한 레코드 전체를
`usedAt` 갱신을 위해 다시 씁니다. 이 쓰기가 실패하면 이미 읽은 사본도 반환되지 않습니다.
[chatDeltaSync.ts](../../src/ts/storage/chatDeltaSync.ts) 63~68행은 예외를 캐시 없음으로 처리합니다.

quota 오류를 주입했을 때 읽기가 `QuotaExceededError`로 실패했지만 기존 사본은 그대로
존재했습니다. 실제 Android에서 quota 오류가 발생했다는 측정은 아닙니다.

수정 방향: 읽은 사본을 반환하고, 사용 시각 갱신만 실패해도 되는 작업으로 분리합니다.
읽기가 가능한 저장소에서 쓰기 실패가 전체 다운로드로 이어지지 않는 검사가 필요합니다.

### A03 — 전송 캐시는 quota 정리 전에 쓰기를 시도

[transferCache.ts](../../src/ts/storage/transferCache.ts) 92~123행은 새 값을 쓴 뒤 512MiB 한도를
정리합니다. 브라우저 quota가 먼저 차면 쓰기와 트랜잭션이 실패하고 정리·재시도 없이 끝납니다.
오류 주입에서 새 사본은 저장되지 않았고 기존 사본은 남았으며 삭제 횟수는 0이었습니다.

수정 방향: quota 실패에 한해 오래된 사본을 정리하고 재시도합니다. 일반 오류와 구분하며,
수용할 수 없는 값 때문에 모든 사본을 계속 지우거나 무한 재시도하지 않도록 제한해야 합니다.
사용자 데이터 내용을 기록하지 않는 로컬 hit/miss/quota 실패 진단도 필요합니다.

### A04 — 삭제한 플러그인 사본이 계속 남음

[nodeStorage.ts](../../src/ts/storage/nodeStorage.ts) 746~760행의 서버 삭제 ACK 뒤에 영속
사본을 지우지 않습니다. `transferCache`에는 삭제 API가 없고, bulk sync도 완료 시 서버에서
사라진 키를 정리하지 않습니다. 삭제된 본문과 SHA/revision이 남아 검증 목록에 계속 포함됩니다.

공간을 낭비하고 활성 데이터의 퇴출을 유발할 수 있습니다. 목록이 100,000개를 넘으면
`slice(0, 100_000)`에 활성 키가 포함되지 않아 캐시가 있어도 값 전체를 받을 가능성도 있습니다.

수정 방향: 인증된 삭제의 성공 응답 후 해당 사본을 제거합니다. bulk sync는 `done`을 확인한
완전한 결과에 대해서만 없는 키를 정리하며, 중단된 스트림에서는 사본을 삭제하지 않습니다.

## A07. 채팅 전송 — HTTP 캐시와 부가 데이터 구분

관련: [server.cjs](../../server/node/server.cjs) 6631행의 `sendChatContent()`,
[nodeStorage.ts](../../src/ts/storage/nodeStorage.ts) 1495행.

합성 자료: 메시지 3개와 1MiB의 결정적 무작위 Base64 메모. 실제 사용자 데이터가 아닙니다.

| 실제 서버, raw HTTP 요청 | 결과 |
| --- | --- |
| 전체 응답, gzip | 본문 789,982 B |
| 같은 메시지 prefix, 새 메시지 0개, 명시적 HTTP validator 없음 | 본문 789,901 B |
| 동일 ETag를 If-None-Match로 전달 | 304, 본문 0 B |

**“채팅 부가 데이터는 변경이 없어도 항상 MB로 재전송된다”는 설명은 정정해야 합니다.**
Express는 기본 weak ETag를 생성하며 정상 브라우저 HTTP 캐시는 이를 재검증할 수 있습니다.

| 실제 데스크톱 Chromium | 실제 HTTP 결과 | CDP 전송량 |
| --- | --- | --- |
| 처음 받는 prefix 응답 | 200 | 약 789KB |
| 같은 prefix 반복 | 304 | 245 B |
| 같은 프로필로 브라우저 프로세스 재시작 후 | 304 | 245 B |
| 메모는 그대로 두고 작은 메시지 하나 추가 | 200 | 789,350 B |
| 추가 후 같은 요청 반복 | 304 | 245 B |

Chromium은 Brotli를 협상했고 CDP 값은 헤더를 포함합니다. 앞의 raw HTTP 표는 gzip 본문만
측정했으므로 두 표의 바이트를 같은 조건의 값으로 직접 비교하면 안 됩니다.
304로 재검증해도 JS `fetch`에서는 캐시된 본문을 포함한 200 응답으로 보일 수 있습니다.
디코딩된 약 1MiB 길이와 실제 통신량을 구분해야 합니다.

브라우저 프로세스 종료만으로 캐시가 사라진다고 볼 수 없습니다. Android OS의 절전·퇴출
정책까지 재현한 실험은 아닙니다.

확실한 최적화 대상은 HTTP 캐시를 재사용하지 못하는 경우와 작은 메시지 변경으로 큰
메모·로어북까지 다시 전송하는 경우입니다. 전체 채팅 validator를 앱의 영속 사본과 연결하면
HTTP 캐시 의존을 줄일 수 있지만, 작은 메시지 추가 시의 메모 재전송까지 해결하지는 못합니다.
메타데이터 별도 validator/차분 또는 전체 채팅 byte delta를 단계적으로 검토해야 합니다.

## A08~A09. 플러그인 동기화의 검증 목록과 저장 비용

A08 관련: [nodeStorage.ts](../../src/ts/storage/nodeStorage.ts) 1135~1139행.
V2 플러그인 preload에서 모든 키를 SHA 목록과 revision 목록에 각각 넣어 POST합니다.
현재 요청 본문은 gzip하지 않습니다. 변경 없는 값 자체는 생략해도 목록 통신은 남습니다.

합성 형식: 키 13바이트, SHA 64자, revision 65자.

| 키 수 | 비압축 요청 본문 | 요청 gzip 적용 시 추정 |
| --- | --- | --- |
| 1,000 | 171,045 B | 62,258 B |
| 10,000 | 1,710,045 B | 621,540 B |

실제 사용자 키 수나 Android 전송량이 아닙니다. 저장소 전체의 작은 validator 하나를 먼저
비교하고, 바뀐 경우에만 키별 목록을 교환하면 동일 상태의 요청을 크게 줄일 수 있습니다.
목록이 필요한 경우 압축도 검토할 수 있습니다.

A09 관련: [nodeStorage.ts](../../src/ts/storage/nodeStorage.ts) 1175행,
[transferCache.ts](../../src/ts/storage/transferCache.ts) 103~120행.
새 키마다 캐시 저장을 기다리고, 각 저장은 전체 메타데이터를 다시 순회·정렬합니다.
100개 작은 값을 저장한 실험에서 전체 순회 100회, 레코드 읽기 5,050회를 확인했습니다.
키가 많아지면 누적 비용은 O(N²)입니다.

수정 방향: 배치 저장 후 한 번 정리하거나, 총량과 사용 시각을 증분 관리합니다.
여러 탭의 동시 쓰기에서도 집계가 맞는지 검증해야 합니다.

## A10. 미배포 캐시 사용량 카드의 HTTP 집계 비용

관련: [cacheUsage.ts](../../src/ts/storage/cacheUsage.ts) 63~74행,
[CacheUsageCard.svelte](../../src/lib/UI/CacheUsageCard.svelte) 42행.

`navigator.storage.estimate()`를 사용할 수 없는 HTTP 환경에서는 모든 채팅을 순회해
JSON 직렬화와 UTF-8 인코딩을 수행합니다. 1MiB 채팅 16개로 16개 전부,
16,777,942바이트가 직렬화되는 것을 확인했습니다. Node+fake-indexeddb에서 약 148ms였으며
Android 실측 시간은 아닙니다.

네트워크 요청은 없지만 CPU·임시 RAM·로컬 DB I/O 비용이 있습니다. 긴 readonly 트랜잭션이
다음 readwrite 캐시 작업을 기다리게 할 수 있으며 화면을 벗어나도 현재 집계는 취소되지 않습니다.
30초 재사용만으로 전체 데이터 크기에 비례하는 작업 자체가 없어지지는 않습니다.

수정 방향: 캐시를 쓸 때 크기 메타데이터도 관리하고 화면에서는 그 값만 합산합니다.
기존 사본의 최초 집계는 지연·분할하거나 수동으로 수행하고 취소 가능하게 합니다.
브라우저 전체 저장 추정치, 캐시 본문 합계, 실제 기기 여유 공간의 구분은 유지해야 합니다.

## A11~A14. 서버의 메모리·CPU·I/O

### A11 — 크기 확인에 BLOB 본문 복사

[chunkStore.cjs](../../server/node/chunkStore.cjs) 147~161행의 `sizeValue()`와
`snapshotCost()`는 raw 값을 `SELECT value`로 가져와 길이를 반환합니다.
실제 db 모듈에서 합성 32MiB raw 값의 크기만 조회했을 때 약 32MiB의 추가 ArrayBuffer가
생겼습니다. 일반 에셋 목록 통계는 이미 SQL `LENGTH`를 사용하므로 모든 에셋 통계의 문제는 아닙니다.
새 DB/archive는 16MiB 초과 시 청크화하므로 해당 raw 경로의 데이터 크기 조건도 구분해야 합니다.

수정 방향: 길이와 chunk marker 판정을 SQL에서 하고 크기만 반환합니다. 저장 형식을 바꿀
필요가 없는 작은 변경 후보입니다.

### A12 — 청크 읽기의 이중 버퍼

[chunkStore.cjs](../../server/node/chunkStore.cjs) 142행은 모든 청크 버퍼를 모아
`Buffer.concat()`합니다. 합성 32MiB 청크 값 읽기에 추가 ArrayBuffer 약 64MiB를 확인했습니다.
크기를 먼저 확인해 결과 버퍼를 한 번 확보하고 청크를 순서대로 복사하는 개선이 가능합니다.
SQLite 행을 읽는 일시 버퍼까지 전부 없어지는 것은 아닙니다.

### A13 — 통계에서도 콜드 스토리지 전체 펼침

[server.cjs](../../server/node/server.cjs) 2898~2917행의 `listColdStorageBackupEntries()`는
모든 콜드 스토리지를 압축 해제·JSON 변환하고 펼쳐진 Buffer 배열을 만듭니다.
8174행의 백업 크기 추정은 이 배열을 크기 합산에만 사용합니다.

통계 화면이나 활성화된 부팅 백업 알림에서 큰 CPU·RAM 비용이 날 수 있습니다.
통계 전용 경로를 분리해 한 항목씩 해제하고, 가능하면 크기 메타데이터를 사용해야 합니다.
일반 재접속의 모바일 MB 전송 원인과는 별개입니다.

### A14 — 작은 버전 확인 전에 전체 저장 강제 실행

[server.cjs](../../server/node/server.cjs) 4397행의 `flushPendingDb()`가 metadata probe 분기보다
먼저 실행됩니다. 저장 대기 중이면 본문 없는 확인 요청도 전체 DB 인코딩·쓰기를 유발할 수 있습니다.
`readRevision()`은 메모리 view와 ETag를 포함하므로 probe를 먼저 처리할 여지가 있습니다.
대기 중 patch·chat 저장, 복원, 가져오기의 일관성을 확인한 뒤 순서를 조정해야 합니다.

## 추가 개선 후보와 큰 변경의 경계

- **닫힌 설정 패널의 토큰 계산:** `App.svelte` 235~239행은 Sidebar를 CSS로 숨깁니다.
  `botMakerMode`가 참이면 `Sidebar.svelte` 1260행의 CharConfig가 남고, CharConfig 74~92행의
  토큰 계산은 보이는지 확인하지 않습니다. 사전/WASM 첫 다운로드를 유발할 수 있으므로
  실제 표시될 때 계산하는 것이 좋습니다. 기본값이 꺼진 조건부 경로입니다.
- **토큰 사전 캐시:** `/token`은 일반 static의 `maxAge:0` 경로입니다. 재검증 304가 가능하므로
  매번 본문 다운로드라는 뜻은 아닙니다. 버전 URL과 장기 캐시를 검토할 수 있습니다.
  원본 사전은 모델별 약 1.8~12.8MB, gzip 추정 약 0.7~3.9MB였습니다.
- **로그 업로드:** `src/ts/log.ts` 77~125행은 항목 수만 제한하고 설명·배치 바이트와 동시 flush를
  제한하지 않습니다. 오류 폭주와 느린 연결이 겹치면 업로드·메모리가 커질 수 있습니다.
  한 번에 한 배치, 바이트 상한, 중복 요약이 적절하며 정상 접속 MB 원인으로 확정되지는 않았습니다.
- **플러그인의 직접 채팅 조회:** `apiV3/v3.svelte.ts` 1004행에서 아직 열지 않은 채팅을 전체
  GET할 수 있습니다. 실제 설치 플러그인의 호출을 확인하고 범위를 줄여야 합니다.
- **DB·플러그인 저장 후 사본:** 채팅과 달리 DB·플러그인 저장 ACK 후 영속 전송 사본을 즉시
  갱신하지 않습니다. 요청 바이트와 서버 정규화 결과가 다를 수 있어 서버가 확인한 validator와
  동일 본문을 저장하는 설계가 필요합니다. 요청 본문을 그대로 최신본이라고 표시하면 안 됩니다.
- **늦게 도착한 채팅 fetch:** 새 저장 ACK 뒤 오래된 fetch가 도착하면 캐시가 옛 상태로 돌아갈
  수 있습니다. prefix 검증이 잘못된 병합은 막지만 추가 전송이 발생할 수 있으므로 세대 번호로
  오래된 응답의 캐시 갱신을 억제하는 방법이 있습니다.
- **중복 동기 압축:** `server.cjs` 4466~4471행은 delta/전체 응답을 동기 gzip으로 비교한 뒤
  선택 응답을 middleware가 다시 압축합니다. 비동기 비교와 선택한 압축 결과 재사용을 검토합니다.
  큰 상시 압축 캐시는 서버 RAM을 늘리므로 별도 예산 없이 추가하지 않는 편이 좋습니다.
- **큰 저장 폴더 이관:** 구버전 ZIP 이관은 전체 수신·압축 해제·복사 버퍼가 겹칩니다. 수동
  대형 이관에는 디스크 기반 스트리밍이 적합하며 평소 재접속 문제와는 구분해야 합니다.
- **느린 WebSocket 소비자:** 연결이 살아 있지만 느린 클라이언트에는 `bufferedAmount`를
  제한하지 않는 프록시 경로가 있습니다. 큰 응답이 겹칠 때를 위한 송신 큐 예산이 필요합니다.
- **전체 활성 채팅 보관·전체 DB 저장:** 서버는 활성 채팅 본문을 `fullChatStore`에 보관하고
  저장 시 전체 DB를 다시 조립·인코딩합니다. 효과가 큰 구조적 개선 후보지만 보존·백업·복원과
  맞닿아 있어 작은 최적화와 분리해 마지막에 검토하는 것이 안전합니다.

## 이미 동작하는 완화책과 주의할 해석

- 메인 DB·플러그인의 revision probe, ETag, byte delta가 이미 구현돼 있습니다.
- 채팅의 40메시지·24개 제한은 v5에서 제거됐습니다. 다시 수정할 항목이 아닙니다.
- 저메모리 SQLite 설정, 불필요한 전체 DB 읽기 제거, 디스크 기반 웹 업데이트 staging은 이미 적용됐습니다.
- 해시된 `/assets` 파일은 1년 immutable 캐시 대상입니다. HTML 직접 참조 파일 크기만으로
  매번 실제 전송량을 계산하면 안 됩니다. JS의 arrayBuffer 길이도 실제 wire 크기와 다릅니다.
- IndexedDB 캐시 코드는 PC·Android에서 같습니다. HTTP IP 접속이나 절전만으로 IndexedDB가
  반드시 비활성화·삭제된다고 설명하면 안 됩니다. 단말·브라우저·접속 origin별 사본은 별개입니다.
- GitHub 전체 release JSON은 서버가 받습니다. 모바일은 축약된 버전 정보를 받습니다.
- 모델 journal·replay는 파일 스트림과 backpressure를 사용하며 terminal job·로그에도 제한이 있습니다.
  모든 서버 큐나 로그가 무제한이라는 결론은 부정확합니다.
