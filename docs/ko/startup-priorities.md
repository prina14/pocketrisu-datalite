# 실측을 기준으로 한 추가 초기화 최적화

`v1.17.0-datalite.10`에 포함하는 변경입니다. GitHub Release 워크플로는 검사·빌드·포터블 기동 확인 후 게시합니다.
앞선 [서버 delta 응답 대기 단축](delta-response-performance.md)을 유지하며 인증·세션·초기 상태의 왕복을 줄였습니다.

## 지시서와 실측의 대응

`load-data` 3.06초 안에 `database-read` 1.84초가, 그 안에 `database-server-read` 1.41초가 포함됩니다.
이들을 합산해서 비율을 계산하면 같은 대기를 여러 번 셉니다. `load-data`는 별도 네트워크 요청이 아니라
첫 화면에 필요한 초기화 전체의 측정입니다. 접속 시작 기준 데이터 준비는 약 3.53초이며 실제 페인트 시간과도 다릅니다.

| 제안 | 판단과 적용 |
| --- | --- |
| `load-data` 병렬 처리·지연 로딩 | DB/백업 설정 조회, DB 적용/플러그인 목록 선읽기 등 이미 독립 작업을 겹칩니다. 이번에는 초기의 작은 인증·설정 요청 자체를 합칩니다. |
| `database-read` 인덱스·쿼리 최적화 | 1.84초는 로컬 DB 쿼리만의 시간이 아닙니다. 캐시 읽기는 0.03초이고, 서버 응답 1.41초와 브라우저 manifest/복원 합계 0.39초가 포함됩니다. 키 조회는 이미 인덱스·기본 키를 사용하므로 인덱스를 추가하지 않습니다. |
| `database-server-read` 요청 통합·압축·캐시 | 기존 delta·조건부 읽기·gzip은 유지하고 전체본 압축 비교를 조기 종료하도록 수정했습니다. 초기 상태 요청 통합도 추가합니다. 새 GraphQL 계층이나 개인 DB용 CDN은 도입하지 않습니다. |
| `import-status`를 백그라운드로 이동 | 0.88초에는 인증과 세션 준비도 포함됩니다. 상태 확인을 생략하면 가져오기 중 DB를 열고 저장하려 할 수 있으므로 확인을 기다리는 순서는 유지하고 왕복 횟수를 줄입니다. |

DB 디코딩·적용은 합계 0.05초이고 플러그인 준비는 0.26초였습니다. 기능 실행 전 준비가 필요한
플러그인을 일괄 idle 작업으로 옮기는 변경은 하지 않습니다.

## 인증이 유지된 접속의 초기 요청 4개 → 1개

기존에는 `/api/test_auth` → `/api/session` → `/api/risu-account/status`가 이어졌고,
백업 알림 설정은 별도 `/api/backup/boot-reminder`로 읽었습니다. 마지막 설정 조회는 이미 DB와 병렬이므로
네 요청의 지연을 모두 직렬 대기 시간으로 계산해서는 안 됩니다.

이제 부팅 때만 `/api/test_auth`에 `x-risu-bootstrap: 1`과 기존 `x-session-id`를 보냅니다.
서버는 기존 JWT/HttpOnly 쿠키 인증이 성공한 뒤 다음 정보를 같은 응답으로 전달합니다.

- 갱신 JWT, 기존 방식의 세션 쿠키·부팅 등록
- 현재 계정 가져오기 상태와 `blocking` 값
- 백업 알림 활성화 여부

서버는 진행 중인 승인된 저장이 끝나기를 기다린 뒤 기존 함수로 부팅을 등록합니다.
새로 열린 기기가 기존 기기의 쓰기 권한을 임의로 가져가지 않습니다. 클라이언트는 세션 준비와
가져오기 차단 확인을 마친 후에만 DB 읽기로 넘어갑니다. 백업 알림 표시 시점도 기존과 같습니다.

응답에는 `bootstrap.v = 1`을 사용합니다. 지원하지 않는 서버, 불완전한 응답과 새 비밀번호 입력이
필요한 접속은 기존 인증·세션·상태 조회로 복귀합니다. 버전이 다른 서버와 클라이언트가 함께 있어도
기존 API를 계속 사용할 수 있습니다. 인증 실패·초기 비밀번호 설정을 건너뛰지 않습니다.

초기 상태는 한 번만 소비합니다. 이후 가져오기 상태 폴링은 항상 서버를 조회합니다.
캐시에 이전 `blocking: false`를 보관해 다음 접속이나 폴링에서 재사용하는 방식은 아닙니다.
JWT와 상태 응답은 `private, no-store`로 제공합니다.

## 확인한 효과와 남는 비용

- 실제 Chromium에서 신규 통합 경로는 초기 요청 1개, 기존 방식 복귀는 4개였으며
  백업 알림 값과 이후 상태 재조회가 유지됐습니다. 실제 NodeStorage 소스·서버를 연결한 별도 하네스이고,
  로그인 UI·DB 렌더링 등 관련 없는 모듈은 대체했습니다. 새 프로덕션 빌드는 사용하지 않았습니다.
- 각 요청을 100ms로 제어한 가상 시계 시험에서 인증·세션·가져오기 상태가 준비되는 시간은
  300ms → 100ms였습니다. 백업 설정과 DB 로딩 시간은 이 비교에 포함하지 않았습니다.
- 사용자의 0.88초가 0.29초로 줄어든다는 의미는 아닙니다. 최초 연결 지연, TLS/VPN 연결,
  서버가 진행 중인 쓰기를 기다리는 시간은 요청 통합 후에도 남습니다.
- 응답 헤더 `Server-Timing`의 `boot-auth`, `boot-session`, `boot-status`로 서버에서 걸린 시간을
  구분합니다. 클라이언트의 기존 `import-status`는 전체 초기 준비 시간을 계속 측정합니다.
- 기존 `database-*`, `plugins` 측정과 서버 `read-*` 시간도 유지합니다. 실제 다음 병목이 인코딩·
  delta 생성·통신 중 어디인지 확인한 뒤 변경하며, 무거운 UI 진단 카드·추가 폴링은 만들지 않습니다.

첫 비밀번호 입력·비밀번호 설정, 구버전 서버 접속에서는 요청 감소가 적용되지 않을 수 있습니다.
고정 IP HTTP 환경과 기존 저장소·백업 형식, 작은 서버의 메모리 한도를 유지하며 의존 패키지는 추가하지 않았습니다.

## 검증 결과

- 앱 **1,809개**, 서버 **247개**, 호환성 **154개** 통과. 앱 3개·호환성 6개 건너뜀.
- 타입 오류 0개, 기존 `DefaultChatScreen.svelte` 접근성 경고 4개.
- 통합 응답·구버전 복귀·불완전 상태 재조회·비밀번호 흐름·최신 상태 폴링과 지연 제어 시험 통과.
- 실제 서버에서 JWT/쿠키 인증·익명 요청 거부·기존 기기의 잠금 유지·가져오기 차단 상태 확인.
- 진행 중인 백업 가져오기가 쓰기 대기 한도를 넘겨도 기존/통합 부팅 모두 완료를 기다리는 것을 검증.
- 실제 Chromium에서 통합 초기 요청 1회와 기존 방식 4회, 백업 설정·이후 상태 갱신 확인.
- 포터블 의존성 목록 변화 없음, `git diff --check` 통과.

v10 배포 준비 시 프로덕션 빌드와 실제 Node 서버·Chromium의 PC 첫 로그인, 모바일 재접속,
큰 DB의 delta 복원·통합 요청 1회·설정 열기/닫기도 확인했습니다. 런타임 예외는 없었습니다.
합성 테스트 DB를 사용하고 외부 인터넷 요청을 차단한 검사로, 실제 Oracle·Android 시간 측정은 아닙니다.
