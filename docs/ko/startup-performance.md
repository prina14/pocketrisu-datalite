# 초기 로딩 구조와 최적화

`v1.17.0-datalite.7`에 포함하는 소스 변경 사항입니다. 로컬 프로덕션 빌드를 완료했으며, GitHub Release 워크플로가 검증 후 Linux x64 포터블을 빌드·게시합니다.

v8의 추가 변경과 외부 CSS 지연 재현 결과는 [첫 화면의 외부 CSS 대기 제거](first-paint-blockers.md)에 기록했습니다.
대량 데이터의 캐시·폴더 목록 변경은 [대량 캐릭터·대화 최적화](large-history-performance.md)에 기록했습니다.
v8 이후 DB 읽기의 병렬 검증·지연 캐시 저장은 [DB 읽기 대기 단축](database-load-performance.md)에 기록했습니다.
이어지는 백업 설정·플러그인 목록 선읽기·캐시 메타데이터 조회 개선은 [독립 작업 동시 실행](startup-parallel.md)에 기록했습니다.

## 로딩 경로

첫 화면까지는 앱 JavaScript 다운로드·실행, 가져오기 상태 확인, 저장소 초기화,
메인 DB 읽기·디코딩·적용, 플러그인 초기화, 형식 확인, 선택한 백업 알림 순서로 진행합니다.
서버의 버전 응답이 작더라도 이 작업들이 모두 없어지는 것은 아닙니다.
특히 V2 플러그인은 기존 동기 저장소 API 때문에 실행 전에 전체 값을 메모리에 준비합니다.
브라우저가 탭을 폐기했다면 JavaScript 실행과 메모리 준비도 다시 필요합니다.

## 대화 우선 최적화 계획

기능을 없애기보다 **처음에 필요한 준비와 실제로 열 때 필요한 준비를 분리**합니다.
이미 진행한 캐시·서버 최적화는 유지하고 다음 순서로 적용합니다.

| 우선순위 | 작업 | 기능 보존 조건 |
| --- | --- | --- |
| 1 · 이번 적용 | Recently Uploaded 기본 접힘, 모바일 초기 화면을 캐릭터 목록으로 변경 | 기존 `hideRealm: false`는 보존. Realm 탭·펼치기·Get More·카드 상세·약관은 사용 가능해야 함 |
| 2 · 이번 적용 | Realm, 빠른 설정, 조건부 관리 창의 코드 지연 로딩 | 모든 초기 정적 진입점을 확인. 닫기·실패·재시도와 선택 콜백 정리를 유지 |
| 3 · 이번 적용 | 캐릭터 목록 이미지의 native lazy loading·비동기 디코딩 | 원본 파일·서버 API·선택한 채팅의 이미지·애니메이션을 변경하지 않음 |
| 3 · 이번 적용 | Lua 런타임과 오류 소스맵 도구를 실제 사용 시 import | 기존 async 대기·초기화 공유·실패 재시도·원본 오류 표시를 유지 |
| 4 · 후속 측정 | `database-decode`·`database-apply`·`format-update`·`plugins`별 실제 기기 시간 확인 | JavaScript 다운로드/실행, 네트워크, DB 처리와 플러그인 준비를 구분 |
| 5 · 후속 변경 | 중복 DB 정규화, 고정 100ms 대화 복원 대기 개선 | 플러그인 index 선읽기는 v9에 반영. DB 읽기/최초 저장 이후 시작하며 실행 전 준비 대기를 유지 |

### 초기 준비를 유지하는 항목

- **인증·가져오기 상태·최신 revision 확인:** 오래된 로컬 사본을 믿고 쓰거나 가져오기 중인 데이터를 덮어쓰지 않아야 합니다.
- **DB 기본값·형식 이관·채팅 placeholder 변환:** 현재 대화와 캐릭터가 유효한 형태여야 화면·플러그인이 안전하게 접근할 수 있습니다.
- **활성 플러그인 초기화:** 플러그인 provider·메시지 변환·커스텀 UI hook이 등록되기 전에 전송을 허용하면 응답 경로나 내용이 달라질 수 있습니다. 특히 V2 동기 저장소는 전체 사전 준비가 필요합니다.
- **모델 등록·모듈 상태·저장 감시·작업 복구:** 대화에 바로 영향을 주므로 이번에는 임의로 idle 작업으로 옮기지 않습니다.
- **사용자가 켠 부팅 백업 알림:** 설정을 병렬로 읽되 알림과 확인 절차를 생략하지 않습니다.

### 지연 로딩의 동작 차이

관리 화면을 처음 열 때 해당 코드의 다운로드·실행 시간이 생길 수 있습니다.
같은 페이지에서 다시 열 때는 브라우저의 모듈 캐시를 사용합니다. 필요하지 않은 기능은
그 페이지에서 한 번도 열지 않으면 불러오지 않습니다. 앱 업데이트 중 파일이 바뀌거나
오프라인이면 해당 화면의 로딩이 실패할 수 있어 재시도·닫기를 제공합니다.

캐릭터 목록은 모바일의 핵심 화면이므로 그대로 초기 경로에 둡니다. 플러그인·저장 루프의
완료 순서를 바꾸거나 polyfill을 한꺼번에 제거하는 작업도 이번 범위에 넣지 않았습니다.
이 부분은 단순히 나중에 실행한다고 동일한 동작이 보장되지 않기 때문입니다.

## 적용한 변경

| 경로 | 변경 |
| --- | --- |
| 메인 페이지 | 캐시 용량 카드와 본문 집계 모듈을 삭제했습니다. 실제 저장 캐시는 유지합니다. |
| 초기 UI 의존성 | 설정 화면의 PC·모바일 진입점, 모델 프로필 브라우저, HypaV3 요약 관리 창을 열 때 import합니다. 로딩 실패 시 재시도·닫기가 가능합니다. |
| 홈·Realm 기본값 | 없는 `hideRealm` 설정과 새 테마 프리셋은 접힘을 기본값으로 둡니다. 기존 `false`는 보존합니다. 모바일은 캐릭터 목록에서 시작하고 Realm은 탭을 누를 때 엽니다. |
| 추가 UI 의존성 | Realm 목록·상세·추천, 빠른 설정, 프리셋·모델·테마·페르소나·메모리 관리, 북마크·에셋 뷰어·팝업 편집기는 해당 화면을 요청할 때 import합니다. |
| 목록 이미지 | 캐릭터 목록·사이드바의 `<img>`에 `loading="lazy"`와 `decoding="async"`를 적용합니다. 브라우저가 화면 근처 이미지부터 읽으며 정확한 선읽기 범위는 브라우저가 결정합니다. CSS 배경 이미지와 선택한 대화 이미지는 유지합니다. |
| 선택 기능 라이브러리 | Lua는 기존 async 런타임 생성 경로에서 불러오며, 오류 소스맵 도구는 오류 상세를 요청할 때 불러옵니다. 수식·다운로드 API는 이번에 변경하지 않습니다. |
| 플러그인 캐시 저장 | 키마다 쓰기 트랜잭션과 전체 메타데이터 스캔을 반복하던 경로를 최대 32개 또는 1 MiB의 배치로 처리합니다. 한도를 초과하는 단일 값은 따로 씁니다. |
| 부팅 요청 순서 | 백업 알림 설정 읽기를 플러그인 초기화와 겹칩니다. 알림 표시와 백업 확인 시점은 유지합니다. |
| 첫 화면 이후 작업 | 저장소 지속성 요청, 앱 업데이트 확인, 공개 통계 요청을 첫 렌더링 기회 뒤에 시작합니다. 각 요청은 서로의 완료를 기다리지 않습니다. |
| 서버 버전 확인 | DB 메타데이터만 확인하는 요청은 대기 중인 전체 DB 저장을 강제로 실행하지 않습니다. 메모리의 최신 revision을 비교하며 실제 본문 읽기는 기존처럼 먼저 저장합니다. |
| 서버 크기 조회 | raw BLOB 본문을 Node로 복사하지 않고 SQLite `LENGTH`와 짧은 청크 marker 검사로 크기를 구합니다. |

배치 캐시는 기존 512 MiB 한도, validator 검증, 오류 시 네트워크 복구를 유지합니다.
배치 저장이 중간에 실패하면 해당 트랜잭션을 취소해 본문과 버전 정보의 불일치를 막습니다.
기존 서버 데이터·백업 형식과 플러그인 API는 바꾸지 않았습니다.

기존 `hideRealm: false`가 예전 기본값에서 온 것인지 사용자가 선택한 것인지는 저장된
데이터만으로 구분할 수 없어 강제로 덮어쓰지 않습니다. 그 값이 남아 있는 PC 홈은 기존처럼
펼쳐지고 1.5초 후 목록을 준비합니다. 사용자가 직접 펼칠 때는 추가 지연 없이 로딩합니다.
설정이 없거나 `true`이면 접힌 상태에서 목록 요청·카드 이미지 로딩을 시작하지 않습니다.

## 확인한 효과와 한계

- 작은 플러그인 키 100개를 처음 저장하는 테스트에서 쓰기 트랜잭션·메타데이터 스캔은 각각 **100회 → 4회**, 읽은 메타데이터 행은 **5,050개 → 292개**였습니다. Node와 fake-indexeddb에서 확인했으며 Android의 실제 시간 측정은 아닙니다. 반복 전체 스캔 자체를 완전히 제거한 방식은 아닙니다.
- 설정·대화상자 분리로 초기 정적 의존 경로에서 기존 소스 67개, 약 679 kB를 분리하고 공통 로딩 컴포넌트 1개를 추가했습니다. 소스 의존 관계 분석이며, 배포 번들의 전송량이나 HTTP 요청 수가 그만큼 감소한다는 의미는 아닙니다.
- 대화 우선 추가 단계에서는 초기 정적 의존 파일이 **418개 → 326개**로 줄었습니다. 이전 단계의 작업 트리를 기준으로 기존 소스 **92개·553,528 B**를 추가로 분리했으며 `source-map`·`wasmoon`·`svelte-awesome-color-picker`도 초기 정적 외부 의존 목록에서 빠졌습니다. 패키지 내부 코드 크기는 위 소스 바이트에 포함하지 않았습니다. 프로덕션 빌드의 실제 전송량은 아직 측정하지 않았습니다.
- 합성 32 MiB raw BLOB의 크기 조회에서 추가 ArrayBuffer 할당이 **32 MiB → 0 MiB**로 줄었습니다. 사용자 서버 전체 RAM이나 전체 로딩 시간의 측정값은 아닙니다.
- 실제 서버 테스트에서 대기 중인 DB patch는 새 revision에 반영되고, 동일한 pending revision은 `304`를 반환하며, probe가 추가 DB 쓰기를 유발하지 않는 것을 확인했습니다. 실제 본문 읽기의 저장과 채팅 내용 보존도 검증했습니다.

캐시가 없는 최초 다운로드, DB 디코딩, V2 플러그인의 전체 메모리 준비, 실제 화면의 이미지 다운로드는 여전히 발생합니다.
사용자의 Android·서버에서 첫 화면이 몇 초 빨라지는지는 아직 실측하지 않았습니다.

## 기기에서 느린 구간 확인

개발자 도구 콘솔에서 다음을 실행하면 부팅 구간별 시간을 볼 수 있습니다. 별도 카드,
저장소 집계, 진단 데이터 전송은 없으며 브라우저의 Performance 측정 항목만 남깁니다.

```js
performance.getEntriesByType('measure')
  .filter(entry => entry.name.startsWith('pocketrisu:startup:'))
  .map(entry => ({ name: entry.name, ms: Math.round(entry.duration) }))
```

`database-read`는 서버 비교·읽기 및 로컬 사본 사용 구간이고,
`database-decode`·`database-apply`는 브라우저 처리, `plugins`는 플러그인 준비 구간입니다.
`load-data`는 데이터 로딩 함수 진입부터 `loadedStore`를 활성화하는 시점까지입니다.
앞선 JavaScript 다운로드·파싱과 이후 실제 화면 페인트는 포함하지 않습니다.
Network 패널과 함께 비교해야 합니다.
병렬 구간은 겹치므로 각 시간을 더해 전체 시간으로 해석하지 않습니다.

## 검증

- 앱 테스트: 1,758개 통과, 3개 건너뜀
- 서버 테스트: 241개 통과
- 호환성 테스트: 153개 통과, 6개 건너뜀
- Svelte/TypeScript 검사: 오류 0개, 기존 `DefaultChatScreen.svelte` 접근성 경고 4개

배치 상한·실패 원자성·중단된 스트림, UI 지연 로딩·재시도·닫기,
선택 작업의 비차단 실행, revision·인증·백업 가져오기 호환성을 검사했습니다.
추가 단계에서는 Realm 기본값·접힘·약관·재시도·모바일 탭 전환, App의 미완료 로딩 취소,
최초 동시 Lua 호출의 초기화 공유·JSON helper 준비 대기도 검증했습니다.

Chromium에서는 실제 MainMenu·RealmBrowser·RealmMain·RealmRecommendations·RealmHubIcon·
MobileBody를 사용하는 별도 하네스로 다음을 확인했습니다. 핵심 상태·서버 API와 모바일의
다른 패널은 테스트용 대체 구현이므로 실제 서버 통합이나 Android 시간 측정은 아닙니다.

| 경로 | 결과 |
| --- | --- |
| PC 기본 접힘 | 1.7초 후에도 목록 함수 호출·Realm 컴포넌트 요청 0회 |
| PC 명시적 펼침·접기 | 목록 호출 1회, 실제 카드 표시 후 접기 정상 |
| 모바일 첫 화면·탭 | 캐릭터 목록에서 호출 0회, Realm 탭에서 호출 1회, 목록 복귀 정상 |
| PC·모바일 약관 미동의 | 목록 호출·카드 이미지 요청 0회, 동의 후 카드 표시 |
| Get More·뒤로가기 | 전체 Realm 검색 화면 진입 후 홈 복귀 정상 |

확인한 경로에서 런타임 예외는 없었습니다. 전체 App을 여는 개발용 하네스는 의존 패키지의
Svelte virtual CSS 변환·로딩 오류로 첫 렌더링에 도달하지 못했습니다. 따라서 설정·빠른 설정·
관리 팝업의 전체 앱 브라우저 검증은 미완료입니다. 지연 경계의 props·닫기·실패 후 재시도와
App의 로딩 중 선택 취소·단축키 취소는 happy-dom 기능 테스트로 확인했습니다.

### 후속 프로덕션 빌드 확인

`corepack pnpm run build`가 성공했고 `dist/`를 생성했습니다. 빌드된 앱을 실제 Node 서버와
임시 저장소에 연결해 Chromium에서 PC·모바일 부팅, 실제 인증·모바일 재접속,
설정 열기·닫기를 확인했습니다. 설정 청크 요청은 첫 열기 전 0회, 연 뒤 1회였고
확인한 경로의 런타임 예외는 0개였습니다. 위 개발용 virtual CSS 장애는 이 경로에서
발생하지 않았습니다. 이 검사는 빈 테스트 DB를 사용했으며 외부 인터넷 리소스는 차단했습니다.
빠른 설정·나머지 관리 팝업의 프로덕션 브라우저 검증과 실제 Android 시간 실측은 남아 있습니다.
빌드에는 CSS 최적화·외부화된 Node 모듈·일부 큰 청크·기존 정적/동적 import 혼용 및
CSS 소스맵 관련 경고가 있지만 빌드 오류는 없습니다.

### DataLite 19: 단순 열람과 본문 변경 구분

캐릭터를 열 때마다 `lastInteraction`을 메인 DB에 기록하던 동작을 독립된 인증 메타데이터로 옮겼습니다.
클라이언트의 최근 목록은 기존 메시지 시각과 별도 열람 시각의 최댓값으로 정렬합니다. 별도 기록은
부팅 후와 열람·브라우저 복귀 때 동기화하며 본문 single-writer lock을 변경하지 않습니다.
메시지 전송과 처음 열 때 필요한 누락 기본값 생성 등 실제 내용 변경은 여전히 동기화 대상입니다.

읽기 revision은 디스크에 일치하는 메모리 뷰를 로드하거나 인코딩한 경우 유지합니다. 미저장 뷰는
별도 token으로 구분하고 같은 값 patch에는 불필요한 저장을 생략합니다. 작은 startup index는
DB의 영속 token 및 앱 버전과 연결하여 저장하며, 검증된 경우 재시작 직후 목록과 기존 ETag를
큰 DB 로드 없이 사용할 수 있습니다. 실제 수정·가져오기·복원 검증은 생략하지 않습니다.

cold delta의 전체 압축 비교 생략 한도를 16 KiB에서 64 KiB로 높이되 전체 raw DB의 1% 조건을
유지합니다. 작은 패킷만 제한된 동기 압축으로 공용 비동기 압축 큐 대기를 피하고, 큰 데이터는
비동기 처리합니다. 실제 DB 읽기가 진행 중이면 선택적인 사전 준비 작업을 미룹니다.

### 로딩 전후의 레이아웃 일치

첫 HTML·앱 내부 로딩 화면이 같은 템플릿과 외부 의존성이 없는 작은 표현 함수를 사용합니다.
정상 로딩 후의 테마 색·글꼴 종류·사이드바 크기·둥근 아이콘·모바일 GUI 설정만 origin-local
`pocketrisu-startup-presentation-v1`에 보관하여 다음 접속의 첫 화면에 적용합니다.
캐릭터 이름·메시지·키·DB 사본은 이 설정에 넣지 않으며 서버 DB를 수정하지 않습니다.

실제 GUI의 1024/1025px 사이드바 경계, 홈 콘텐츠 최대 폭·카드·아이콘 배치, 모바일 검색창·
행 높이·하단 메뉴 크기를 맞췄습니다. 테두리 색 변수도 실제 GUI와 같은 소문자
`--risu-theme-darkborderc`를 사용합니다. 한국어 공용 라벨은 인증된 캐릭터 목록을 기다리지 않고 표시합니다.
캐시 값은 길이·필드·스타일 값 형식을 제한하고, 네트워크 URL이나 사용자 HTML을 적용하지 않습니다.

최초 방문에는 로컬 표현 설정이 없으므로 기본 틀을 사용합니다. 캐릭터 이미지·최근 대화 내용은
기존 인증 및 데이터 로딩 순서에 따르며, 로딩 화면 때문에 외부 이미지·폰트·Realm 목록을 추가 요청하지 않습니다.
사용자가 임의로 작성한 CSS 전체나 모든 조건부 배너까지 미리 복제하는 방식은 아닙니다.

검증은 전체 프로덕션 재빌드 없이 기존 정상 앱과 변경한 첫 HTML/CSS를 같은 임시 Node 서버에서
비교했습니다. 1200·1600px PC, 1024px 경계, 390px 모바일 및 모바일 GUI를 끈 390px에서
주요 위치와 크기를 확인했습니다. PC의 사이드바·홈 첫 카드와 모바일 검색창·첫 행·하단 메뉴
측정값이 일치했습니다. 새 HTML의 실제 Vite 변환·인라인 코드 문법 검사와 공유 표현 함수·
인증된 미리보기 검사 10개도 통과했습니다. 첫 앱 빌드와 Oracle/Android 실측을 대체하는 검사는 아닙니다.
