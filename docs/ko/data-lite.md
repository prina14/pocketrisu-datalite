# 모바일 재접속 전송량 줄이기

이 작업본은 PocketRisu v1.17.0 (`40851fc9831856a36cb5c14799c1f501f32dc133`)을 기준으로 합니다.
기존 서버 데이터와 `.bin` 백업 형식은 바꾸지 않습니다.

## 변경 사항

- **플러그인 저장소:** V2 사전 로딩과 V3 전체 저장소 읽기에서 브라우저의 IndexedDB에 사본을 보관합니다. 재접속하면 키와 SHA-256 목록을 서버에 보내고, 서버는 변경된 키만 갱신합니다. 큰 값은 아래의 조각 동기화를 사용합니다. 삭제된 키는 결과에 포함하지 않습니다. 같은 길이의 수정, 백업 가져오기와 복원도 현재 내용으로 비교합니다.
- **V3 개별 읽기:** 필요한 키만 읽는 플러그인도 같은 사본을 공유하며, 서버에서 값이 그대로인지 확인한 뒤 재사용합니다.
- **메인 DB:** 시작할 때 사본의 버전을 서버에 확인합니다. 같으면 본문 없는 304 응답을 받고 사본을 사용합니다. 다르면 변경된 부분만 받아 최신 DB를 복원합니다.
- **조각 동기화:** 128 KiB 이상인 DB·플러그인 값에 사본이 있으면, 내용 기준으로 나눈 조각의 SHA-256 목록을 보냅니다. 서버는 같은 조각을 가리키는 작은 정보와 새 조각만 돌려줍니다. 중간에 텍스트가 추가·삭제돼도 이후의 조각을 재사용할 수 있습니다. 비교 목록도 gzip으로 압축합니다. 서버에 과거 사본을 보관할 필요가 없어 서버 재시작·백업 복원 후에도 동작합니다.
- **복원 검증:** 복원한 전체 값의 SHA-256이 서버와 일치해야 사용합니다. 맞지 않거나 응답이 잘렸다면 전체 값을 한 번 다시 받습니다. 데이터가 대부분 바뀌어 조각 전송이 더 크면 서버가 전체 응답을 선택합니다.
- **호환성:** 동기 API인 V2도 실행 전에 모든 값을 메모리에 준비합니다. 원격 저장소를 읽거나 쓰는 API와 백업은 그대로 유지합니다. 구버전 서버에서는 기존 전체 다운로드로 돌아갑니다.
- **HTTP IP 접속:** HTTPS 전용 CacheStorage와 Web Crypto에 의존하지 않아 HTTP IP 접속에서도 IndexedDB를 쓸 수 있습니다.

캐시는 동일한 접속 주소·브라우저에만 적용되고 최대 512 MiB까지 보관합니다. 오래 전에 저장된 사본부터 제거합니다. 브라우저 용량 제한이 더 작거나 사본이 사라지면 필요한 값을 다시 받습니다. 캐시 접근이 불가능해도 앱은 네트워크로 계속 동작합니다.

사본을 사용하기 전에 항상 서버 인증과 내용 비교를 수행합니다. 서버에 연결할 수 없거나 인증에 실패했을 때 오래된 사본으로 시작하지 않습니다. 로컬 사본에는 개인 대화·플러그인 데이터가 포함될 수 있으며, 브라우저의 해당 사이트 데이터 삭제로 제거할 수 있습니다.

## 적용

코드 수정만으로 운영 중인 서버가 바뀌지는 않습니다. 이 소스로 프런트엔드를 다시 빌드하고 수정된 Node 서버와 함께 배포해야 합니다. 최초 접속에서는 사본을 만들기 위한 다운로드가 필요하며, 두 번째 접속부터 효과가 나타납니다.

Node.js 22.12 이상에서 이 저장소 루트를 작업 디렉터리로 사용합니다.

```bash
corepack pnpm install --frozen-lockfile
corepack pnpm run build
corepack pnpm run runserver
```

운영 데이터는 작업 디렉터리의 `save/`, 백업은 `backups/`에 있습니다. 새 경로로 옮긴다면 기존 서버를 중지하고 두 디렉터리를 백업·이전한 뒤 시작하세요. 포터블 실행 파일이나 기존 배포 이미지에는 이 수정이 자동으로 들어가지 않습니다. 공식 업데이트로 이 작업본을 대체하면 수정도 사라질 수 있으므로 별도 배포본으로 관리해야 합니다.

## 효과 확인

같은 주소로 한 번 접속한 뒤 페이지를 다시 열고 개발자 도구 Network에서 비교합니다.

- `/api/plugin-storage/sync` 응답에는 변경되지 않은 값 대신 `null`과 버전만 있어야 합니다.
- 큰 사본은 `/api/read-delta`로 비교 목록을 보내고, 작은 값이나 사본이 없는 값은 `/api/read`로 읽습니다. 그대로라면 304여야 합니다.
- 응답 헤더 `x-read-resource`는 `database` 또는 `plugin-storage`로 읽은 데이터의 종류를 표시합니다. `x-read-transfer`는 `delta`(부분), `unchanged`(동일), `full`(전체)을 표시합니다. `x-read-full-bytes`는 복원된 전체 값의 크기이므로 실제 전송량과 혼동하지 마세요.
- 큰 플러그인 값 하나를 조금 수정한 뒤 다시 접속하면 해당 값의 변경된 조각만 받고, 나머지 키는 사본을 사용해야 합니다.

초기 접속, 캐시 삭제 후 접속, 새 빌드의 앱 파일, 이미지·동영상·외부 플러그인의 자체 통신은 여전히 데이터를 사용합니다. 변경된 부분을 전송하므로 값 전체가 교체되면 전체를 다시 받을 수도 있습니다. 큰 사본의 비교 목록도 업로드 데이터에 포함됩니다. 실제 하루 사용량의 감소율은 운영 데이터로 측정해야 합니다.

## 테스트 측정 예시

실제 Node 서버에 3 MiB의 난수를 base64로 표현한 플러그인 문자열을 넣고, 중간에 짧은 내용을 삽입한 뒤 gzip HTTP 본문을 측정했습니다. 복원 결과의 SHA-256도 원본과 일치했습니다.

| 요청 | 요청 본문 | gzip 응답 본문 |
| --- | ---: | ---: |
| 최초 전체 읽기 | 없음 | 3,159,040 B |
| 중간에 짧은 내용 추가 후 부분 읽기 | 16,567 B | 9,533 B |
| 내용이 그대로인 재접속 | 비교 목록 | 0 B (304) |

이는 해당 읽기 요청 한 건의 예시입니다. HTTP 헤더, 인증 통신, 앱 파일, 다른 DB·이미지 등의 전송량과 실제 하루 사용량은 포함하지 않습니다. 데이터 수정·삭제·가져오기, 로컬 캐시 유실과 저장 실패, 구버전 서버 대응은 별도 테스트로 확인합니다.

## Windows에서 기존 설치 업데이트

Git으로 설치했다면 서버를 종료하고 저장소 폴더의 PowerShell에서 실행합니다.

```powershell
git pull origin main
pnpm.cmd install --frozen-lockfile
pnpm.cmd run build
pnpm.cmd run runserver
```

ZIP으로 설치했다면 저장소의 최신 ZIP을 새 폴더에 풀고, 서버를 종료한 뒤 기존 `save/`와 `backups/`를 복사합니다. 새 폴더에서 위의 `pnpm.cmd` 명령 세 개를 실행하세요. 기존 데이터 폴더와 백업 원본은 남겨두세요. 새 앱 파일을 받는 첫 접속 이후에, 같은 주소·같은 브라우저로 재접속하며 측정합니다.
