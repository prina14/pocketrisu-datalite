# 서버 delta 응답 대기 단축

`v1.17.0-datalite.10`에 포함하는 변경입니다. GitHub Release 워크플로는 검사·빌드·포터블 기동 확인 후 게시합니다.

## 측정에서 고른 대상

사용자가 제공한 부팅 측정은 `load-data` 3.06초, 접속 시작 기준 데이터 준비 완료 약 3.53초였습니다.
그중 `database-server-read`가 1.41초로 가장 길었고, `import-status`가 0.88초였습니다.
캐시 읽기는 0.03초, DB 디코딩·적용은 합계 0.05초였습니다. 이번 변경은 가장 긴 delta 응답 경로에 집중합니다.
1.41초 전체가 서버 CPU 시간이라는 뜻은 아닙니다. 통신·요청 전송·대기도 포함됩니다.

## 압축 크기 비교를 일찍 끝내기

기존 서버는 raw delta가 전체본의 80%보다 작으면, gzip을 지원하는 요청에서 차이본과 전체본을
각각 `gzipSync`로 끝까지 압축해 크기를 비교했습니다. 수 KB의 차이본을 보내기 위해 수 MB의 전체본을
압축하며, 이 동기 작업 중에는 Node 이벤트 루프의 다른 요청 처리도 대기합니다.

이제 차이본은 비동기 gzip으로 크기를 구하고, 전체본은 64 KiB씩 하나의 gzip 스트림에 넣습니다.
전체본의 압축 출력이 차이본의 정확한 압축 크기를 **초과하는 순간** 차이본이 더 작다는 것이
확정되므로 스트림을 중단합니다. 입력을 한 번에 모두 큐에 넣지 않고 이전 쓰기가 끝나야 다음을 넣습니다.
전체본의 압축 출력은 크기만 세고 버리므로 비교용 전체 gzip 버퍼도 만들지 않습니다.

- 전체본이 더 작거나 같은 경우에는 끝까지 확인하고 기존처럼 전체본을 선택합니다.
- 중간 flush를 추가하지 않아 기존 gzip 크기와 동일한 기준으로 비교합니다.
- raw 80% 조건, 기존 gzip 비교 정책·HTTP 압축 협상·응답 압축 middleware를 유지합니다.
- delta 형식, SHA-256 복원 검증, ETag·revision과 인증을 바꾸지 않습니다.
- 프로세스에 큰 DB 사본이나 압축 결과를 추가로 보관하는 캐시는 만들지 않습니다.

최종 응답 압축은 기존 middleware가 담당하므로 선택한 본문의 응답용 압축은 여전히 발생합니다.
DB 인코딩, 전체 바이트의 chunk·해시 계산, 클라이언트 manifest 생성·복원도 이번 변경에 남습니다.
실제로 변경되지 않았으면 기존 revision/ETag `304` 경로를 사용하고 압축 비교에 진입하지 않습니다.

## 동일 데이터의 HTTP 비교 결과

로컬 임시 서버 두 개를 순서대로 사용했습니다. 4 MiB 난수의 base64 문자열을 포함한 동일 DB에서
사용자 이름만 바꾸고, 워밍업 1회 뒤 각 방식 5회씩 gzip HTTP 요청을 측정했습니다.
비교군은 다른 코드·응답 경로를 유지하고 압축 크기 비교만 기존 `gzipSync` 방식으로 대체했습니다.

| 항목 | 기존 전체 압축 비교 | 조기 종료 비교 |
| --- | ---: | ---: |
| 전체 응답의 복원 전 원본 바이트 | 5,592,505 B | 5,592,505 B |
| 비교용 전체본 압축에 넣은 바이트 | 5,592,505 B | 65,536 B |
| 압축 비교 시간 중앙값 | 111.67ms | 5.70ms |
| HTTP 응답 전체 수신 시간 중앙값 | 166.26ms | 61.77ms |
| 압축된 응답 본문 | 4,309 B | 4,309 B |
| 압축된 요청 manifest | 23,398 B | 23,398 B |

모든 응답의 delta 복원 SHA-256과 본문 전송 바이트가 일치했습니다. 위 전송량은 HTTP 본문만이며
새 진단 헤더를 포함한 HTTP 헤더는 제외합니다. 합성 DB·로컬 루프백 측정으로, 사용자 Oracle 서버·
Android의 실제 개선율이나 1.41초가 위 수치로 줄어든다는 보장은 아닙니다.
전체본이 잘 압축되거나 차이본도 크면 전체 비교를 끝내야 해 조기 종료 효과가 작을 수 있습니다.

## 실제 서버에서 구간 구분

읽기 응답의 `Server-Timing`에 다음 단계를 기록합니다. 새 UI·폴링·진단 데이터 업로드는 없습니다.

| 항목 | 의미 |
| --- | --- |
| `read-auth` | 해당 읽기 요청의 서버 인증 처리 |
| `read-revision` | 본문 없이 revision 확인하는 경로 |
| `read-flush` | 대기 중인 DB 저장 반영 |
| `read-load` | DB가 아직 준비되지 않았다면 로드·작업 큐 대기 |
| `read-encode` | 클라이언트용 DB 인코딩 |
| `read-value` | KV 값 읽기와 주변 처리 |
| `read-hash` | 본문 validator와 revision 준비 |
| `read-delta` | 차이본 생성·무결성 해시 계산 |
| `read-compress-compare` | 압축 크기 비교 |

`x-read-compare-bytes`는 gzip 비교에 넣은 전체본 입력 바이트입니다. 비교를 하지 않은 응답에는 없습니다.
Network에서 `read-delta`의 Timing/응답 헤더로 확인하거나 콘솔에서 다음을 실행합니다.

```js
console.table(performance.getEntriesByType('resource')
  .filter(e => new URL(e.name).pathname === '/api/read-delta')
  .flatMap(e => Array.from(e.serverTiming || [], t => ({ 단계: t.name, ms: t.duration }))));
```

이 측정은 route 진입 이후 구간이며 요청 업로드·본문 파싱, 최종 응답 압축·수신과 프록시 대기를
모두 포함하지 않습니다. `read-auth` 역시 앞선 부팅 `import-status` 0.88초 전체와 다른 측정입니다.

## 검증

- 압축 비교 변경을 처음 검증한 시점: 앱 **1,797개**, 서버 **247개**, 호환성 **153개** 통과. 앱 3개·호환성 6개 건너뜀.
- 타입 오류 0개, 기존 `DefaultChatScreen.svelte` 접근성 경고 4개.
- gzip 크기 경계의 엄격한 비교·동일 크기·고압축 전체본 선택·이벤트 루프 양보·부분 복원 검증.
- 실제 서버에서 DB/플러그인 delta, gzip 전체본 선택과 identity delta 선택, revision·인증·메모리 회귀 확인.
- 기존 v9 프런트엔드 빌드와 수정 서버를 Chromium에 연결해 큰 DB의 PC 첫 접속, 서버 수정 후 모바일
  재접속의 실제 `read-delta`·복원·설정 열기/닫기 확인. 런타임 예외 0개.
- 포터블 서버 의존성 목록 변화 없음. 이 모듈 검증 시점에는 새로운 프로덕션 빌드를 실행하지 않았으며, 배포 준비 검증은 릴리스 노트에 기록합니다.
