# 서버 메모리 최적화

`v1.17.0-datalite.3`은 1GB Oracle 서버와 같은 작은 서버의 메모리 부담을 줄입니다.

## 전체 DB 중복 읽기 제거

`/api/read`와 `/api/read-delta`의 DB 읽기는 이미 준비된 클라이언트용 DB가
있어도 먼저 `kvGet('database/database.bin')`으로 채팅 본문까지 포함한 전체
저장본을 메모리에 읽고, 그 결과를 클라이언트용 DB로 덮어쓰고 있었습니다.
캐시가 없을 때는 초기화 과정에서도 같은 저장본을 다시 읽었습니다.

이제 존재 여부는 기존 revision 메타데이터로 확인합니다. 캐시가 없을 때만
전체 DB를 한 번 읽고, 이후 요청은 클라이언트용 DB를 사용합니다. 재접속 때의
불필요한 BLOB 할당과 디스크 읽기를 줄입니다. 버전 확인, ETag, 차분 전송,
인증 및 저장 큐의 동작은 유지됩니다.

## 작은 서버의 자동 메모리 설정

시작할 때 물리 RAM과 Node.js가 감지한 컨테이너 메모리 제한 중 작은 값을
기준으로 프로필을 선택합니다. 용량이 **2GiB 이하**이면 `low`를 사용합니다.
현재 남은 메모리로 선택하지 않으므로 다른 프로그램 사용량에 따라 설정이
달라지지 않습니다.

| 설정 | 기존/standard | low |
| --- | --- | --- |
| SQLite 페이지 캐시 목표 | 64,000KiB | 8,192KiB |
| SQLite 파일 매핑 최대 크기 | 256MiB | 0 (사용 안 함) |
| SQLite 임시 저장소 | MEMORY | FILE |
| 에셋 목록 캐시 한도 (JSON 크기 기준) | 64MiB | 8MiB |

이 값들은 프로세스 전체 RAM 제한이나 사전 할당량이 아닙니다. 특히 파일
매핑으로 보이는 RSS에는 운영체제가 회수할 수 있는 파일 캐시도 포함됩니다.
캐시를 줄이면 반복 작업에서 디스크 읽기와 에셋 목록 재해석이 늘 수 있습니다.
SQLite 임시 파일은 기존 설정대로 `save/`에 기록됩니다
(`SQLITE_TMPDIR`을 지정했다면 그 경로).

필요하면 서버 실행 환경변수로 선택할 수 있습니다.

```bash
POCKETRISU_MEMORY_PROFILE=low ./start.sh
POCKETRISU_MEMORY_PROFILE=standard ./start.sh
```

기본값은 `auto`이며, 서버 시작 로그의 `[Memory] low profile` 또는
`[Memory] standard profile`로 적용 여부를 확인할 수 있습니다.
`POCKETRISU_ASSET_MANIFEST_CACHE_BYTES`를 이미 설정했다면 그 값이 우선합니다.
자동 실행 서비스는 해당 서비스의 환경변수 설정을 사용합니다.

## 확인 범위

- 실제 서버 통합 테스트에서 초기 전체 DB 읽기 1회, 이후 반복 읽기·ETag
  확인·revision 확인·동일 데이터 차분 요청의 추가 전체 DB 읽기 0회를 확인합니다.
- 기존 저장 데이터, 백업, 채팅, 차분 전송에 대한 회귀 검사를 수행합니다.
- 개발 환경에서 1MiB 행 128개를 쓰고 체크포인트한 뒤 읽는 독립 프로세스
  비교에서는 SQLite 설정 변경으로 익명 상주 메모리가 약 59MiB 줄었습니다.
  파일 매핑 영역 감소는 이 수치에서 제외했습니다. 합성 데이터와 개발 환경의
  결과이며 실제 Oracle 서버의 절감량을 보장하는 값은 아닙니다.

채팅 본문을 보관하는 `fullChatStore`의 저장 구조나 수명은 바꾸지 않습니다.
큰 채팅·플러그인 값·백업 가져오기는 여전히 상당한 메모리를 사용할 수 있고,
이 패치가 서버 전체를 일정 메모리 이하로 제한하지는 않습니다.
