# 대량 캐릭터·대화 최적화

`v1.17.0-datalite.8`에 포함하는 변경입니다. 앞선 외부 CSS·편집기 지연 로딩 수정도
유지하며, 후속 요청에 따라 프로덕션 빌드와 GitHub Release 검증을 진행합니다.

## 시험 데이터와 적용 범위

| 상황 | 데이터 | 확인 |
| --- | --- | --- |
| 많은 대화 목록 | 대화 10,000개, 폴더 200개 | 기존 목록 계산과 같은 인덱스 합계·순서, 조회 횟수·시간 비교 |
| 매우 큰 목록 | 대화 100,000개, 폴더 1,000개 | 폴더 정보 1회씩만 읽고 메시지 본문은 전혀 읽지 않음 |
| 긴 채팅 캐시 | 메시지 20,000개, 메시지당 텍스트 250자 | 본문 재쓰기 없이 사용 시각 갱신, quota 실패 때도 읽기 성공 |
| 캐릭터 목록 | 두 접힌 폴더 안의 캐릭터 1,000개와 바깥 1개 | 행 1개만 생성, 폴더 열기·닫기 때 생성·해제 |
| 폴더 순서 저장 | 접힌 폴더 안의 캐릭터 10,000개 | DOM에 없는 내부 캐릭터의 소속·순서를 보존하며 폴더 재정렬 |

합성 데이터와 로컬 개발 환경의 결과이며 사용자의 실제 Oracle·Android 시간 측정은 아닙니다.

## 1. 대화 목록을 한 번만 인덱싱

폴더 하나마다 전체 `chats`를 두 번 필터링하고, 각 행의 원래 위치를 다시 `indexOf`로
찾던 경로를 `indexChatsByFolder()`로 바꿨습니다. 폴더별 원본 참조와 배열 인덱스를
한 번 계산합니다. 이름 편집·복사·삭제·내보내기, 빈 폴더와 고아 폴더 처리는 유지합니다.
확인 대화상자를 기다린 뒤 실행하는 복사·삭제는 기존처럼 현재 위치를 다시 조회합니다.

Node에서 동일한 대화 10,000개·폴더 200개를 계산한 결과:

| 경로 | 폴더 정보 조회 | 시간 |
| --- | ---: | ---: |
| 기존 필터·위치 검색 | 4,000,000회 | 128.24 ms |
| 인덱스 사용 | 10,000회 | 1.81 ms |

두 결과의 원본 슬롯 인덱스 합계는 49,995,000으로 같았습니다. 시간은 목록 계산만의
단일 합성 측정으로 전체 페이지 로딩 시간이나 UI 렌더링 개선율이 아닙니다.
별도 100,000개 기능 테스트에서도 본문 getter에 접근하면 실패하도록 설정해
목록 준비가 메시지를 펼쳐 읽지 않는 것을 검증했습니다.

## 2. 캐시 사용 시각을 본문과 분리

이전에는 캐시를 읽을 때 최근 사용 시각을 갱신하려고 대화 본문 전체를 IndexedDB에
다시 썼습니다. 긴 채팅일수록 큰 복사·쓰기 비용이 발생하고, 그 쓰기가 quota로 실패하면
유효한 캐시 읽기도 실패해 다시 다운로드할 수 있었습니다.

로컬 `pocketrisu-chat-copies`를 version 2로 이관해 작은 `recency` 저장소에서 시각만
갱신합니다. 이전 `chats` 본문은 유지하고 기존 인덱스의 키·시각만 읽어 이관합니다.
최근 사용 순 정리·8개 단위 quota 회수 정책은 유지합니다. 실제 본문 갱신과 메타데이터는
하나의 트랜잭션으로 저장해 부분 반영을 막습니다. 사용 시각 갱신 실패는 읽기 결과에 영향을 주지 않습니다.

실제 Chromium의 IndexedDB에 version 1 캐시와 20,000개 메시지를 넣은 뒤 수정 모듈로
읽었습니다. 이관 중 본문 쓰기는 0회, 다음 읽기에서도 본문 쓰기는 0회·작은 메타데이터 쓰기는
1회였습니다. 메타데이터 쓰기에 quota 오류를 넣어도 20,000개 메시지를 그대로 반환했습니다.
동기·비동기 quota 실패, 트랜잭션 롤백, LRU 정리, 구버전 캐시 읽기는 자동 테스트로도 확인합니다.

이는 **브라우저 캐시**의 이관입니다. 서버 저장 파일과 백업 형식은 변경하지 않습니다.
이관된 캐시를 이해하지 못하는 구버전 탭은 기존 오류 처리에 따라 네트워크로 읽을 수 있습니다.

## 3. 같은 긴 대화를 열 때 재저장 생략

서버가 기존 메시지 접두부를 검증하고 새 메시지·부가 정보가 모두 같으면
메시지 배열·fingerprint 배열을 재사용하고, 전체 snapshot과 캐시 본문 재저장을 생략합니다.
메타데이터 비교에서는 메시지 배열을 제외하므로 본문을 다시 비교하지 않습니다.
메모·로어북·필드 삭제·null 등 메타데이터가 바뀌면 기존처럼 최신 전체 사본을 저장합니다.
변경 메시지의 fingerprint 검증·불일치 시 전체 읽기·저장 순서 보호는 유지합니다.

20,000개 메시지 재접속 테스트에서 저장소 읽기의 방어 복사 1회만 남고,
추가 전체 snapshot과 캐시 쓰기는 0회인 것을 검증했습니다. 캐시 읽기 자체와
서버 접두부 비교용 fingerprint 계산은 여전히 필요합니다.

## 4. 접힌 캐릭터 폴더의 행을 생성하지 않음

CSS로 숨기기만 하던 폴더 내부를 실제로 열 때 생성합니다. 폴더 소속을 DOM만으로
저장하면 렌더링하지 않은 캐릭터가 폴더 밖으로 이동할 수 있어, 접힌 폴더는 원래 저장된
소속 목록을 합쳐 순서를 저장하도록 처리했습니다. 기존 펼침·접힘 설정은 유지합니다.

실제 Svelte 컴포넌트의 기능 렌더링 시험에서 접힌 폴더 안 1,000개 캐릭터는 행을 생성하지
않고 바깥 1개만 생성했습니다. 한 폴더를 열면 501개, 다시 접으면 1개로 돌아왔습니다.
Sortable 드래그 라이브러리와 행 표시는 시험용 대체 구현을 사용하되 실제 부모의 레이아웃
수집과 순서 복원·재구성을 실행해 폴더를 옮긴 뒤의 소속을 확인했습니다.

## 남는 비용

- 열지 않은 채팅은 기존 placeholder 방식으로 유지합니다. 저장된 메시지나 캐릭터를 삭제·축약하지 않습니다.
- 펼친 큰 폴더·많은 독립 행의 DOM 생성, 전체 DB 메타데이터 처리, 긴 대화의 최초 읽기·fingerprint 계산은 남습니다.
- 서버가 보유한 전체 대화의 상주 구조와 V2 플러그인의 동기 저장소 사전 준비는 이번에 바꾸지 않았습니다.
- 대화 수가 많을수록 필요한 추가 가상화·서버 읽기 구조 변경은 드래그 정렬·저장·백업 호환성 검증과 함께 별도로 적용해야 합니다.
