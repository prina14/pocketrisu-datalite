# 데이터 준비 이후 초기화와 화면 측정

`v1.17.0-datalite.11`에 포함하는 변경입니다. [delta 경계 계산 개선](delta-boundary-performance.md)과 함께 적용합니다.

## 1.63초와 2.24초의 차이

사용자 측정의 `load-data`는 약 1.63초에 끝나고, 선택적 캐시 저장은 약 2.15초에 시작해
2.24초에 끝났습니다. `load-data`는 `loadedStore` 활성화까지의 데이터 준비 측정으로, 물리적인
화면 표시 완료나 모든 네트워크 작업의 완료를 뜻하지 않습니다. 마지막 캐시 저장 완료 역시
화면을 사용할 수 있는 시각을 직접 측정하는 값은 아닙니다.

두 지점 사이에는 저장 동기화 기준 준비, ID 검사, 모듈 상태 준비, Svelte DOM 업데이트와
브라우저 프레임 스케줄링 등이 들어갑니다. 사용자 로그만으로 약 0.52초를 이 중 특정 함수에
전부 귀속하지 않습니다. 이번에는 저장 기준 준비 중 실제 수행하는 큰 문자열 집계를 줄이고
부팅 측정에서 빠져 있던 구간을 분리합니다.

## 저장 기준 초기화의 바이트 집계

`RisuSavePatcher.init`은 변경 비교용 JSON과 해시 기준을 준비하며 JSON의 UTF-8 크기도 집계합니다.
기존에는 큰 문자열도 JavaScript로 UTF-16 문자 하나씩 검사했습니다.

이제 4,096 UTF-16 코드 유닛 이상의 문자열은 `TextEncoder.encodeInto`와 재사용하는 **64 KiB**
버퍼로 크기를 셉니다. API가 실제 소비한 UTF-16 길이만큼 진행하므로 버퍼 경계의 이모지도
정확히 처리하며, 전체 문자열 크기의 바이트 배열을 만들지 않습니다. 작은 문자열, API가 없는
브라우저, API가 실패하거나 진행하지 못하는 경우에는 기존 계산으로 돌아갑니다.
입력 문자열도 최대 16 Ki UTF-16 코드 유닛으로 제한하고 이모지 쌍의 중간에서 자르지 않습니다.
큰 JSON 문자열의 나머지 전체를 매번 전달해 브라우저에서 반복 변환 비용이 생기는 것을 피합니다.

해시·정규화·변경 비교 기준과 저장 감시 설치 순서는 바꾸지 않았습니다. 저장 준비를 늦춰
초기 사용자의 변경을 놓치거나, 필수 플러그인 초기화를 끝내기 전에 입력을 허용하는 방식은 아닙니다.
이 함수는 저장 중 변경된 항목의 크기 계산에도 사용되므로 같은 경로의 이후 비용도 줄입니다.

로컬 Node의 문자열 집계 단독 시험(워밍업 3회, 측정 7회 중앙값):

| 데이터 | 기존 | 변경 후 |
| --- | ---: | ---: |
| 16 MiB ASCII 문자열 | 36.60ms | 0.70ms |
| 한글·이모지 혼합, UTF-8 30 MiB | 35.38ms | 29.72ms |

문자 구성·브라우저에 따라 효과가 다릅니다. 전체 저장 기준 초기화, 사용자 기기의 0.52초 또는
화면 로딩 전체를 측정한 결과는 아닙니다.

## 추가한 Performance 항목

| 항목 | 범위 |
| --- | --- |
| `save-baseline-init` | 저장 동기화 기준 초기화의 완료까지 |
| `post-data-init` | `load-data` 종료 후 이어지는 초기화의 동기 실행 구간 |
| `navigation-to-ui-frame` | navigation 시간 원점부터 UI 준비 이후 첫 프레임 렌더링 기회 뒤의 콜백까지 |

`navigation-to-ui-frame`은 기존 `scheduleAfterFirstPaint`의 첫 콜백에서 기록하고, 이후 선택적 캐시
저장을 시작합니다. Svelte DOM 업데이트·브라우저 스케줄링이 포함될 수 있으며, 물리적 디스플레이의
실제 페인트나 모든 이미지·네트워크·플러그인 후속 작업 완료를 보장하는 브라우저 이벤트는 아닙니다.
백그라운드 탭에서는 프레임 스케줄링이 제한될 수 있으므로 전경 탭끼리 비교합니다.

기존 콘솔 명령으로 새 항목도 볼 수 있습니다.

```js
console.table(performance.getEntriesByType('measure')
  .filter(e => e.name.startsWith('pocketrisu:startup:'))
  .map(e => ({ 단계: e.name.replace('pocketrisu:startup:', ''),
    시작초: +(e.startTime / 1000).toFixed(2), 소요초: +(e.duration / 1000).toFixed(2) })));
```

`navigation-to-ui-frame`의 소요초는 navigation 이후의 경과 시간입니다. 다른 항목은 서로 포함되거나
겹칠 수 있으므로 모든 시간을 더해 총 로딩 시간으로 계산하지 않습니다. 별도 UI·네트워크 요청·진단
업로드는 추가하지 않았습니다.

## 검증

- 앱 1,821개, 서버 251개, 호환성 154개 통과. 앱 3개·호환성 6개 건너뜀.
- Svelte/TypeScript 오류 0개, 기존 접근성 경고 4개.
- 긴 ASCII·한글·이모지·고립 surrogate·버퍼/입력 경계에서 기존 UTF-8 크기와 일치.
- 입력 16 Ki 코드 유닛·버퍼 64 KiB 한도, 구형 브라우저·API 실패·진행 중단 대체 경로 확인.
- v11 프로덕션 빌드와 실제 Chromium에서 PC 첫 로그인·모바일 재접속의 큰 DB delta 복원·
  설정 열기/닫기, 새 측정 항목과 UI 프레임 기회 이후 캐시 저장을 확인. 런타임 예외 0개.
- 별도 브라우저 프로브에서도 실제 메인 메뉴 DOM이 프레임 측정 전에 구성되는 것을 확인했습니다.
  합성 테스트 DB·로컬 서버·외부 요청 차단 환경이며 실제 Oracle·Android 측정은 아닙니다.
