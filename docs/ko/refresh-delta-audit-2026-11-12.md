# 새로고침·기기 전환 때 DB 변경분을 다시 받는 경로 점검

대상은 DataLite 19입니다. 운영 서버에 접속하거나 사용자 DB·플러그인 원문을 수집하지 않았습니다.
사용자가 제공한 세 측정 기록, 소스 및 임시 Node 서버·Chromium 재현을 근거로 구분했습니다.
사용자의 반복 시험은 PC 단일 접속이므로 그 시험에 다른 기기의 저장을 원인으로 가정하지 않습니다.

## 확인된 사실

### 새로고침 경고는 실제 변경의 증거가 아니다

`src/preload.ts`의 `preLoadCheck()`는 `beforeunload`에 무조건 `preventDefault()`와
`returnValue`를 설정합니다. 실제 미저장 수정 여부를 검사하지 않습니다. 브라우저의 사용자
활성화 조건에 따라 경고가 나타나므로, 아무것도 수정하지 않았어도 표시될 수 있습니다.
조작 없는 정상 페이지에서도 이벤트가 취소되는 것을 확인했습니다. 실제 변경·저장 중·입력 초안을
보호하는 조건을 마련한 뒤 조건부 경고로 바꿔야 하며, 단순히 저장 경고를 전부 없애는 수정은 하지 않았습니다.

### 서버가 계속 바뀌지 않아도 같은 변경분을 반복해서 받을 수 있다

`src/ts/storage/nodeStorage.ts`의 `persistDbCopy()`는 전송 사본의 IndexedDB 저장 실패를
`catch(() => {})`로 무시합니다. `database-cache-write` 측정이 있다는 사실만으로 저장 성공을
확인할 수 없습니다. 사본을 저장하지 못하면 이전 사본을 다음 접속에서도 사용할 수 있습니다.
그 사본과 서버가 다르면 같은 변경분을 다시 요청합니다.

합성 DB에서 변경 한 번을 만든 뒤 서버 내용을 고정하고, main DB 사본의 IndexedDB `put`만
실패하게 했습니다. 세 번의 재접속 모두 서버 ETag가 유지되고 실제 수정은 없었지만 변경분을
다시 받았습니다. 실패를 해제한 접속에서 한 번 동기화한 뒤 다음 접속은 변경분 요청이 없었습니다.
이것은 가능한 경로를 재현한 것이며 사용자의 저장소가 부족하다고 확정한 것은 아닙니다.

### 플러그인의 실제 수정과 같은 값 재설정은 구분해야 한다

| 합성 시험 | 결과 |
| --- | --- |
| 플러그인 없이 독립된 모바일·PC 사본으로 13회 접속·새로고침·전환 | DB 변경과 변경분 요청 없음. 각 기기의 첫 다운로드는 별도 발생 |
| 시작 1.1초 뒤 같은 설정 값을 다시 넣는 V3 플러그인, 4회 | 누락 기본값이 처음 저장된 뒤 한 번 동기화. 이후 DB 변경·delta 없음. 빈 patch 요청은 남음 |
| 시작 1.1초 뒤 매번 다른 설정 값을 넣는 V3 플러그인, PC 단일 접속 4회 | 매번 본문 변경, 브라우저 사본은 그 직전 상태. 다음 접속마다 delta 발생 |
| 플러그인 전용 키의 값만 매번 갱신하는 V3 플러그인, PC 단일 접속 4회 | 초기 기본값 동기화 이후 메인 DB 변경·delta 없음. 플러그인 저장 요청은 별도 발생 |
| DB 사본 저장만 실패시킨 PC, 실패 3회 및 복구 | 서버 수정 없이 같은 delta 반복. 사본 저장 복구 후 반복 중단 |

테스트 플러그인은 원인 경로를 검증하려고 만든 최소 코드입니다. 사용자에게 설치된 특정 플러그인의
문제로 판정하지 않았습니다. 실제 설정 필드가 바뀌는지 확인하려면 해당 환경의 patch 경로 또는
캐시/서버 validator 변화를 추가로 봐야 합니다.

## 모바일에서 접속한 뒤 PC에서 접속하면

- 단순 접속 등록·JWT/세션 갱신·모바일 GUI 선택은 본문 DB 수정과 구분됩니다. GUI 선택은 Svelte store를 변경합니다.
- PC와 모바일의 IndexedDB 사본은 독립적입니다. 두 사본이 모두 최신이면 작은 확인 후 재사용할 수 있습니다.
- 모바일에서 실제 대화·설정·플러그인 초기화로 본문이 수정됐고 PC 사본이 이전 상태라면 PC가 변경분을 받는 것은 정상입니다.
- 처음 사용하는 브라우저·시크릿 세션·다른 origin(IP/도메인/포트/HTTP·HTTPS)은 사본을 공유하지 않아 전체 읽기가 필요할 수 있습니다.
- 메인 DB가 아닌 플러그인 전용 저장소 변경은 그 저장소의 동기화 대상입니다. 메인 DB까지 항상 다시 받을 이유가 되지는 않습니다.

## 측정 기록을 해석할 때

사용자의 세 기록에는 `database-delta-apply`가 있고, 압축해제된 패킷은 모두 23,231B였습니다.
실제 본문 비교가 필요한 경로를 반복해서 탄 것은 확인할 수 있습니다. 그러나 그것만으로
서버가 매번 새로 수정됐는지, 이전 브라우저 사본을 계속 사용했는지는 구분할 수 없습니다.
`load-data`와 그 내부 측정은 겹치므로 합산하지 않습니다. `event-loop-recent-max`도 최근 지연의
참고값이며 해당 요청의 단계 시간과 더하지 않습니다.

## 운영 환경에서 구분하는 작은 진단

[브라우저 진단 코드](diagnostics/check-db-sync.browser.js) 전체를 로그인된 페이지의 콘솔에서 실행합니다.
캐시 메타데이터만 읽고 2초 간격으로 총 세 번 본문 없는 revision 확인을 합니다. DB 수정·캐시 삭제·전체 DB
다운로드를 하지 않으며 인증 토큰과 대화 내용을 출력하지 않습니다. 정상 사본/뒤처진 사본에서 각각
세 번의 확인을 실제 Chromium에서 검증했습니다.

빠른 새로고침 직후와 반복 delta가 나타나는 새로고침 직후 결과를 비교하면 다음을 구분하는 데 도움이 됩니다.

- `서버revision관측중변경: true`: 관측 중 본문 관련 저장 상태가 바뀌었습니다. 그 자체로 변경 필드나 작성자를 뜻하지는 않습니다.
- 서버 revision은 고정인데 확인값이 계속 불일치: 사본이 뒤처져 있습니다. 최근 자동 저장 후 미갱신·캐시 저장 실패·빠른 이탈 등을 추가로 구분해야 합니다.
- 같은 브라우저에서 새로고침을 반복해도 이전 캐시 ETag가 그대로이고 서버 revision도 그대로: 사본 저장/갱신 경로를 우선 확인합니다.
- 캐시/서버 값이 접속마다 함께 달라짐: 자동 초기화·플러그인 patch의 실제 변경 필드를 우선 추적합니다.

저장 URL 횟수는 부팅 이후 현재 페이지의 기록이며, `/api/write`만으로 메인 DB와 플러그인 쓰기를 구분할 수는 없습니다.
해당 진단은 캐시 메타데이터를 확인하며 사본 전체의 무결성을 재검증하는 도구는 아닙니다.

## DataLite 20에 반영한 개선

빈 patch 전송을 생략하고, 실제 본문 저장 승인 후 캐시를 백그라운드에서 갱신합니다.
편집 상태/편집 ETag는 변경하지 않으며 늦게 끝난 과거 읽기의 캐시 교체도 막습니다.
캐시 갱신용 읽기만 승인된 메모리 뷰를 사용할 수 있고, 일반 읽기 flush 및 부팅 재검증은 유지합니다.
서버 patch에서 이미 인코딩한 바이트를 재사용하고 사본 저장 실패를 진단에 기록합니다.
무조건 이탈 경고는 제거하되 미저장·입력·생성·플러그인 저장·편집창은 보호합니다.

진단 코드는 v2로 확장하여 저장 요청의 시작/완료 시각과 최근 40개 동기화 기록을 포함합니다.
이 기록의 root 필드 이름으로 자동 저장이 어느 종류의 값을 바꿨는지 확인할 수 있습니다.
`사본최신: false`는 작은 메타데이터 검사로 동일성을 확인하지 못했다는 뜻입니다.
revision 불일치만으로 실제 바이트 차이를 확정할 수는 없습니다. 관측 구간에 revision이 고정돼
있다는 사실 역시 부팅 직후의 자동 저장이나 그 이전의 변경이 없었다는 뜻은 아닙니다.
