# 최신 전송 완성본 재사용과 작은 캐릭터 목록 선행 표시

v1.17.0-datalite.15에 포함합니다. HTTP API·delta 패킷·저장/백업 형식의 호환성을 유지하면서
서버의 반복 계산과 실제 캐릭터 이름이 표시되기 전의 대기를 줄였습니다.

## 작은 목록을 전체 DB보다 먼저 표시

`GET /api/startup-preview`는 인증된 요청에만 이름 최대 40개와 전체 개수·revision·언어를 반환합니다.
휴지통 항목은 제외하고 이름은 128 UTF-16 코드 단위로 제한합니다. 설명·이미지·채팅·플러그인 코드·
전체 설정을 포함하지 않습니다. 최악의 제어문자 이스케이프도 포함해 작은 응답으로 제한합니다.

- 경량 main 진입점이 기존 HttpOnly 세션 쿠키로 목록을 요청하며, 앱 본체의 import와 병렬로 진행합니다.
- 쿠키가 유효하면 앱 본체·전체 CSS·DB 다운로드가 끝나기 전에 실제 이름을 정적 레이아웃에 표시합니다.
- 첫 로그인은 비밀번호 입력을 거친 뒤 JWT로 목록을 요청하고, 전체 DB 읽기와 병렬로 진행합니다.
- 목록은 텍스트만 표시합니다. 선택·채팅·편집은 기존 플러그인·저장 준비가 끝난 뒤 가능합니다.
- 목록 결과를 DBState·저장 기준·사용자 설정으로 적용하지 않습니다. 전체 DB 적용 이후 늦게 도착한 목록은 무시합니다.
- 인증·가져오기 차단 확인을 서버에서 수행하고, 차단 중이거나 상태 확인에 실패하면 목록을 반환하지 않습니다.
  첫 로드가 큐에서 기다리는 중 가져오기가 시작된 경우도 다시 확인합니다.
- 새로운 writer 세션을 만들거나 권한을 가져오지 않으며, Cache-Control은 private, no-store입니다.
- 최대 2초의 선택적 대기 후 실패하면 기존 부팅을 이어 갑니다. 저장소나 로컬 파일에 이름을 추가 보관하지 않습니다.
  구형 서버에 API가 없을 때도 전체 DB 로딩으로 동작합니다.

현재 endpoint는 첫 화면용 목록을 분리한 것입니다. 완전히 독립된 캐릭터별 DB로 저장 구조를
바꾼 것은 아니며, 정상 앱 준비를 위해 전체 DB 전송은 여전히 진행됩니다.

## 서버의 전송 완성본과 조각 정보

서버가 현재 client-view DB를 읽은 뒤 다음을 최신 한 버전만 재사용합니다.

1. 채팅 본문과 큰 자산 목록을 제외한 기존 형식의 전송 바이너리와 기존 ETag.
2. 전송 바이너리의 gzip 결과. 비동기로 압축하며 같은 버전의 진행 중인 작업도 공유합니다.
3. delta 조각의 시작·길이·SHA-256, 전체 값의 SHA-256.

저장 큐 작업 이후 약 1초의 대기를 두고 현재 view의 완성본을 준비합니다. 연속 작업은 대기를
합치며, 이미 준비됐으면 같은 작업을 반복하지 않습니다. 차가운 요청에서는 필요한 결과를
그 자리에서 만들고 이후 재사용합니다. 서버 재시작 후에는 메모리 캐시를 다시 준비합니다.
디스크에 과거 버전 파일을 계속 쌓는 방식은 아닙니다.

캐시 적중은 현재 view 객체와 ETag가 모두 같을 때만 허용합니다. 데이터 교체·패치·복원으로
view/ETag가 달라지면 새 완성본을 사용하고, 명시적 DB 무효화 시 캐시를 비웁니다.
진행 중인 응답은 시작할 때 잡은 불변 바이트를 사용하며, 오래된 압축 완료가 최신 항목을 덮지 않습니다.

delta 조각 정보도 **같은 바이트 배열**에 속한 경우에만 재사용합니다. 구버전과 동일한 경계·패킷을
생성하며 전체 SHA-256 검증과 실패 시 전체 읽기 복구를 유지합니다. 전체 gzip이 준비돼 있으면
작은 delta만 압축해 실제 길이로 비교합니다. 준비되지 않았으면 기존의 최대 조기 종료 비교를 사용합니다.

캐시 기본 상한은 **64 MiB**이며, raw·gzip 바이트와 조각 메타데이터 추정량을 집계합니다.
노드 전체 RSS나 진행 중인 요청·압축 작업의 순간 메모리 사용량까지 64 MiB라는 뜻은 아닙니다.
예산 초과 항목은 요청 처리 후 보관하지 않고 해당 시점부터 선택적 백그라운드 준비를 중단합니다.
전경 읽기에서 보관 가능한 크기의 새 완성본이 준비되면 다시 사용할 수 있습니다.

`POCKETRISU_READ_SNAPSHOT_BYTES` 환경변수로 상한을 바꿀 수 있습니다. `0`은 완성본 보관과
선택적 사전 준비를 끕니다. 최신 한 버전만 보관하므로 PC·모바일·탭 수만큼 사본을 유지하지 않습니다.

gzip을 허용한 DB 응답은 준비된 gzip을 그대로 보내며 중복 HTTP 압축을 하지 않습니다.
`gzip;q=0`과 identity 요청은 해당 표현으로 처리합니다. 인증과 private, no-store 정책은 유지합니다.

## 검증과 효과

v14 소스의 실제 Node 서버와 수정 서버에 같은 약 **12.65MB 합성 DB**를 저장하고,
동일한 구버전 manifest로 5회씩 로컬 HTTP 요청을 보냈습니다. 서버 완성본 사전 준비 후 중앙값입니다.

| 요청 | v14 | 수정 후 |
| --- | ---: | ---: |
| 전체 응답 | 163.83ms | 6.35ms |
| delta 응답 | 81.84ms | 4.20ms |

전체 gzip 본문 **3,185,093 B**, delta gzip 본문 **15,587 B**로 두 서버의 응답 크기가 같았습니다.
압축 해제한 전체 값·delta 패킷의 SHA-256과 복원 결과도 일치했습니다.
이 수치는 로컬 합성 시험의 준비된 서버 응답 시간이며 Oracle·Android의 실제 로딩 개선율이 아닙니다.
같은 바이트를 전달하므로 느린 회선에서 첫 전체 다운로드가 오래 걸리는 현상 자체를 없애지는 않습니다.

프로덕션 빌드·실제 Node 서버·Chromium 시험에서는 다음을 확인했습니다.

- 앱 본체 파일 응답을 멈춘 상태에서도 인증된 이름 두 개가 정적 레이아웃에 먼저 표시됐습니다.
- DB 요청을 인위적으로 5초 지연한 PC 시험: 목록 렌더링 기회 **111ms**, 전체 DB 적용 후 미리보기 **5,581ms**.
- 같은 환경의 모바일 화면: 목록 **140ms**, 최종 UI 렌더링 기회 **238ms**. 캐시가 있는 재접속 시험입니다.
- 쿠키·브라우저 저장소를 지운 첫 로그인: 로그인 전 이름 미노출, 입력 후 목록 **159ms**, 전체 DB 적용 후 **5,224ms**.
  비밀번호 입력은 자동 시험이므로 사용자 입력 시간을 대표하지 않습니다.
- PC 설정 열기/닫기, 모바일 부팅, 미디어·편집 제어 없는 초기 목록, 런타임 예외 없음.

앱 **1,840개**, 서버 **273개**, 호환성 **154개** 통과. 앱 3개·호환성 6개 건너뜀.
타입 오류 0개, 기존 접근성 경고 4개. 네이티브 서버 의존성 목록은 변경되지 않았습니다.
인증·세션 권한, 가져오기 차단, 패치·백업 복원, gzip 협상과 무결성은 별도로 검증했습니다.

## 사용자 기기에서 확인

기존 부팅 측정 명령을 그대로 사용할 수 있습니다.

- `navigation-to-shell-frame`: 기본 레이아웃 렌더링 기회.
- **`navigation-to-list-frame`**: 작은 API에서 받은 실제 이름의 첫 렌더링 기회.
- `navigation-to-preview-frame`: 전체 DB 적용 뒤의 미리보기 렌더링 기회.
- `navigation-to-ui-frame`: 기존 최종 UI 렌더링 기회.
- `startup-preview-read`: 첫 로그인 등에 필요한 인증된 작은 목록 요청.

위 값은 화면을 그릴 기회를 측정하며 실제 물리적 출력이나 모든 백그라운드 작업 완료를 보장하지 않습니다.
상하위 항목은 겹치므로 시간을 합산하지 않습니다. 첫 콘텐츠의 실제 관측은 FCP도 함께 확인합니다.

DB 응답의 `x-read-snapshot: hit`는 완성본 재사용입니다. `read-encode`·`read-hash`·`read-delta`에서
변화를 볼 수 있고, **`read-compress`**는 전체 응답을 보내기 전에 준비한 gzip 대기를 포함합니다.
`x-read-compare-bytes: 0`은 준비된 전체 gzip 길이를 사용해 비교한 경우입니다.
