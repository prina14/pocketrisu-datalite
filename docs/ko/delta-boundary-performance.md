# delta 조각 경계 계산 단축

`v1.17.0-datalite.11`에 포함하는 변경입니다. GitHub Release 워크플로는 검사·빌드·포터블 기동 확인 후 게시합니다.

## 실측에서 선택한 작업

사용자가 제공한 서버 `Server-Timing`의 합계는 약 604ms였습니다.

| 구간 | 시간 |
| --- | ---: |
| delta 생성 `read-delta` | 406.19ms |
| DB 인코딩 `read-encode` | 127.53ms |
| validator 준비 `read-hash` | 53.53ms |
| 압축 크기 비교 | 15.09ms |
| 저장 반영·인증·로드 등 | 합계 약 1.4ms |

네트워크 패널의 delta 응답 약 640ms 중 상당 부분이 서버 처리였습니다. 가장 큰 delta 생성부터 개선합니다.
`load-data`와 `database-read`에는 이 응답 대기가 포함되므로 이 부분의 단축이 상위 구간에도 반영됩니다.

## 같은 경계·패킷을 더 적은 연산으로 계산

서버와 브라우저가 공유하는 `server/node/readDelta.mjs`의 조각 경계 계산 부분을 변경했습니다.

1. gear 표를 `Int32Array`로 보관하고 rolling 값도 signed int32로 계산합니다. 기존 unsigned 값과
   사용하는 하위 비트가 같으므로 경계 판정 결과는 같습니다.
2. 최소 조각 크기 2,048 B 이전에는 경계가 생길 수 없습니다. rolling 식이
   `r = (2r + gear[byte]) mod 2^32`이므로 32번 이동하면 이전 상태의 영향은 사라집니다.
   첫 판정 직전 31바이트만 준비하고 판정 위치의 1바이트를 처리해 기존과 같은 상태를 만듭니다.
3. 최대 크기 32,768 B는 내부 루프의 종료 위치로 제한합니다. 매 바이트마다 최소·최대 크기를
   다시 계산하고 분기하지 않습니다. 최소 크기보다 짧은 마지막 조각은 그대로 반환합니다.

이는 데이터 경계 규칙을 바꾸는 것이 아니라 같은 규칙을 계산하는 비용을 줄이는 변경입니다.
조각의 시작·크기·해시·순서와 delta 패킷은 v10과 같아야 합니다. 기존 브라우저 사본을 버리거나
새 전송 형식을 협상하지 않습니다. SHA-256 복원 검증과 실패 시 전체 읽기도 유지합니다.

`makeManifest`·`makeDelta`·`applyDelta`가 같은 함수를 사용하므로 서버 delta 생성뿐 아니라
브라우저의 manifest·복원 경계 계산에도 적용됩니다. 전체 SHA-256, 서버 DB 인코딩·validator 계산,
브라우저 본문 복사는 남아 있으므로 이 작업들의 전체 시간이 같은 비율로 줄어드는 것은 아닙니다.
추가 DB 캐시·워커·의존 패키지는 만들지 않았습니다.

## 로컬 비교 결과

### 실제 HTTP 서버

같은 12 MiB 난수의 base64 문자열을 넣은 DB에서 사용자 이름만 변경했습니다.
대조군은 v10 `makeDelta`를 사용하고, 다른 서버 코드·압축 비교·응답 경로는 같게 유지했습니다.
각 방식은 임시 서버를 순서대로 사용해 워밍업 1회 뒤 5회 측정한 중앙값입니다.

| 항목 | v10 | 변경 후 |
| --- | ---: | ---: |
| 전체 응답의 원본 바이트 | 16,777,313 B | 16,777,313 B |
| 서버 delta 생성 | 115.72ms | 50.88ms |
| HTTP 전체 응답 수신 | 207.93ms | 154.08ms |
| 압축된 요청 manifest | 68,481 B | 68,481 B |
| 압축된 응답 본문 | 7,726 B | 7,726 B |

모든 응답의 본문 전송량과 복원 SHA-256이 일치했습니다. HTTP 헤더는 바이트 비교에서 제외했습니다.
사용자 Oracle·Android의 실제 개선율이나 406ms가 위 수치가 된다는 보장은 아닙니다.

### 실제 Chromium 경계 계산

16 MiB 난수, 워밍업 3회 뒤 7회 측정한 중앙값은 **79.50ms → 13.80ms**였습니다.
1,708개 조각의 시작·크기가 모두 같았습니다. 실제 소스 모듈의 분리된 시험이며 전체 앱 로딩이나
Android의 0.19초 계산 구간 전체를 측정한 값은 아닙니다.

## 호환성 검증

- v10의 원래 경계 계산을 독립 참조 구현으로 유지해 빈 값·최소/최대 경계 주변 길이·짧은 tail을 비교합니다.
- 0~255 모든 바이트의 반복 입력과 UTF-8 JSON·난수·패턴·offset이 있는 Buffer/Uint8Array를 검사합니다.
- 삽입·삭제·재정렬·반복 조각·빈 값에서 v10 manifest와 패킷 바이트의 SHA-256 일치, 전체 복원을 검증합니다.
- 기존 v10 프로덕션 클라이언트와 새 서버를 Chromium에서 연결해 PC/모바일 부팅·서버 수정 후 delta 복원·
  통합 초기 요청·설정 열기/닫기를 확인했습니다. 런타임 예외는 없었습니다. 새 프런트엔드 빌드는 하지 않았습니다.
- 앱 **1,809개**, 서버 **251개**, 호환성 **154개** 통과. 앱 3개·호환성 6개 건너뜀.
- 타입 오류 0개, 기존 `DefaultChatScreen.svelte` 접근성 경고 4개.
- 포터블 서버 의존성 목록 변화 없음, `git diff --check` 통과.
