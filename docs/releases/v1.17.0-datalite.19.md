# PocketRisu DataLite 19 — 열람 후 재접속과 서버 초기 대기 개선

단순히 캐릭터를 열어 본 뒤 재접속하는 경우에도 큰 DB를 다시 동기화하던 요인을 줄였습니다.
작은 변경분을 보내기 위해 큰 DB 전체 압축을 기다리는 경로도 줄였습니다.

## 변경

- 캐릭터를 열 때 기록하는 최근 열람 시각을 메인 DB에서 분리했습니다. 인증된 작은 KV 메타데이터로 저장하며 최근 목록·정렬에 기존 대화 시각과 함께 반영합니다. 이 기록은 본문 저장 권한을 가져오지 않고, 부팅 완료 후·화면 복귀·열람 시 동기화합니다. 주기적인 실시간 폴링은 추가하지 않았습니다.
- DB를 메모리에 읽거나 전송용으로 인코딩했다는 이유만으로 읽기 revision이 바뀌지 않도록 했습니다. 아직 디스크에 반영되지 않은 실제 수정은 별도 pending revision으로 구분합니다.
- 값이 동일한 patch는 저장·DB 캐시 교체를 생략합니다. 인증·저장 권한·충돌 검사는 그대로 수행합니다.
- 최대 40개 캐릭터 이름과 전송 ETag를 작은 파생 인덱스로 보관합니다. 현재 DB의 저장 token과 앱 버전이 일치하면 서버 재시작 후에도 큰 DB를 로드하지 않고 목록을 표시하거나 동일한 브라우저 사본을 확인할 수 있습니다. 미저장 수정·가져오기·복원 시 검증 조건을 통과하지 못하면 기존 읽기 경로를 사용합니다.
- 전송량 64 KiB 이하이고 raw 크기가 전체 DB의 1% 이하인 cold delta는 전체 압축 크기 비교를 기다리지 않습니다. 전체 압축본이 이미 있으면 정확히 비교합니다. 예외적으로 전체 압축본이 더 작은 경우 추가 본문은 최대 64 KiB로 제한됩니다.
- raw 64 KiB 이하 변경 패킷은 제한된 동기 네이티브 압축으로 처리하여 큰 비동기 압축 작업의 공용 작업 큐 대기를 피합니다. 큰 값은 비동기 압축을 유지합니다.
- 실제 DB 본문 읽기가 진행 중이면 선택적인 사전 준비를 미룹니다. 조각 인덱스 작업자 런타임은 서버 시작 시 빈 입력으로 준비합니다.

실제 메시지 전송·설정 수정·처음 열 때 필요한 기본값 생성·플러그인 저장은 여전히 본문을 바꿀 수 있습니다.
처음 받는 DB나 캐시 삭제, 느린 통신, 플러그인 실행 시간이 사라지는 변경은 아니며 모든 접속의 1초 완료를 보장하지 않습니다.
기존 설치 경로·HTTPS 설정·저장 형식과 본문 저장 권한 정책은 유지합니다.

## 검증

- 실제 서버에서 열람 기록의 인증·조건부 읽기·본문 revision 불변·다른 기기의 저장 권한 유지, 같은 값 patch와 실제 pending 수정 구분을 확인했습니다.
- SQLite 온라인 백업으로 재시작 상황을 구성하여 작은 목록 캐시 적중 및 이전 ETag의 무본문 확인을 검증했습니다.
- 16 KiB를 넘는 작은 cold delta가 지연된 전체 Brotli 압축을 기다리지 않는 회귀 검사를 추가했습니다.
- 앱 1,852개·서버 283개·호환성 154개 통과. 앱 3개·호환성 6개 건너뜀. 타입 오류 0개, 기존 접근성 경고 4개.
- 프로덕션 빌드·실제 Node 서버·Chromium에서 PC 설정, 모바일, 최초 로그인 전 이름 비노출, 늦은 목록 인계를 확인했습니다. 런타임 예외는 없었습니다.
- 약 11.44MB 합성 DB에서 기본값을 한 번 동기화한 뒤 캐릭터를 다시 열어도 본문 ETag·revision이 유지되고, 재접속은 `304` 경로를 사용했습니다. 실제 내용 수정은 네이티브 해시·delta 경로로 정상 반영했습니다. 로컬 시험이며 Oracle·Android의 동일 시간을 보장하지 않습니다.

## 업데이트·측정

Linux x64 포터블을 제공합니다. 기존 커스텀 자동 업데이트로 적용할 수 있으며 서버에서 직접 빌드할 필요가 없습니다.

**기존 통합 콘솔 코드를 그대로 사용하면 됩니다.** 브라우저 캐시를 지우지 않은 상태에서 다음을 비교해 주세요.

1. 업데이트 후 첫 접속.
2. 단순 새로고침.
3. 캐릭터를 열고 입력·설정 변경 없이 돌아온 뒤 재접속.
4. 실제 메시지를 저장한 뒤 재접속.

`navigation-to-list-frame`, `navigation-to-ui-frame`, `database-version-check` 및 변경분 단계의 유무를 확인해 주세요.
서버 응답 헤더의 `x-startup-preview-cache: hit`와 `x-read-index-validator: 1`은 작은 파생 인덱스를 재사용한 경우 표시됩니다.
`event-loop-recent-max`는 최근 서버 지연의 문맥이며 다른 요청 단계 시간과 더하지 않습니다.
