# PocketRisu DataLite 22 — 준비된 변경분을 버전 확인 응답으로 전달

재접속 시 서버가 이미 계산한 변경분을 바로 전달하고, 브라우저의 반복 해시 계산과
앱 파일의 서버 압축을 줄였습니다. v21의 저장 실패 복구·캐시 갱신·조건부 이탈 보호를 유지합니다.

## 변경 사항

- **준비된 변경분:** 최근 최대 4개 사본의 조각 정보에 맞춰 최신 DB로 가는 delta와 gzip·Brotli 결과를 유휴 시점에 준비합니다. 과거 DB 본문 전체나 접속자/IP 이력을 보관하지 않습니다.
- **왕복 생략:** 브라우저가 실제 가진 ETag/revision으로 확인했을 때 완성된 변경분이 있으면 `/api/read`의 버전 확인 응답에 바로 보냅니다. 적중 시 별도 manifest 업로드와 `/api/read-delta` 왕복을 생략합니다. 없으면 기존 경로를 사용합니다.
- **브라우저 조각 정보 재사용:** DB 사본을 저장할 때 조각 정보도 같은 IndexedDB 트랜잭션에 보관합니다. 이후 변경분 요청에서 전체 사본의 조각 해시를 다시 계산하지 않습니다. 기존 캐시도 그대로 사용할 수 있습니다.
- **앱 파일 사전 압축:** 빌드할 때 JS·CSS의 gzip/Brotli 파일을 만듭니다. 사용자 서버에서는 준비된 파일을 협상해 전송합니다. 기존 빌드·압축 거부·범위 요청은 기존 정적 파일 경로로 처리합니다.
- **플러그인 진단:** V3 플러그인마다 iframe/bridge 및 최상위 비동기 코드 완료까지의 시간과 상태를 기록합니다. DB 변경 API 요청은 플러그인 이름·메서드·최상위 필드만 기록합니다. 요청했다는 기록이 실제 데이터 변경을 뜻하지는 않습니다.

인증·writer 권한·충돌 검사·SHA-256 복원 검사·전체 읽기 복구를 생략하지 않습니다.
서버가 예전에 전송했다는 이유로 브라우저의 저장 성공을 가정하지 않습니다. 일반 전경 읽기의
디스크 flush도 유지합니다. 브라우저 사본이 최신이면 기존처럼 본문 없는 304를 반환합니다.

## 효과와 범위

12,654,443 B 합성 DB의 같은 이전 버전 → 최신 버전을 로컬 HTTP에서 각각 5회 비교했습니다.
준비된 변경분이 있는 경우 요청 수는 2 → 1, 확인부터 복원·검사까지의 중앙값은 52.26 → 30.39ms였습니다.
압축 delta는 두 버전 모두 8,114 B이며 패킷·복원 해시가 일치했습니다.
이는 로컬 시험이며 전체 앱이나 Oracle·Android의 개선율을 뜻하지 않습니다.

같은 새 JS 파일을 기존 Brotli 품질 4와 빌드 시 품질 6으로 비교하면 appEntry는
177,540 → 164,508 B, database 모듈은 537,276 → 483,055 B였습니다. 캐시된 정적 파일은
원래 재다운로드하지 않으므로 주로 첫 접속·새 릴리스 다운로드에 도움이 됩니다.

서버 재시작·새 사본·연속 저장 직후에는 준비된 결과가 없을 수 있습니다. 모든 재접속이
즉시 처리된다는 뜻은 아닙니다. 플러그인 실행 순서나 실제 자동 변경을 임의로 차단하지 않습니다.
대화 화면의 준비 의존성을 바꾸는 대규모 분할도 이번 변경에 포함하지 않습니다.

## 설치와 테스트

Linux x64: `PocketRisu-v1.17.0-datalite.22-linux-x64.tar.gz`와 같은 이름의 `.sha256`.
기존 커스텀 자동 업데이트를 사용하면 설치 폴더·데이터·systemd·HTTPS 설정을 유지합니다.

화면 표시 후 약 10초 뒤 [통합 진단 v3](../ko/diagnostics/check-db-sync.browser.js)를 실행하세요.
기존 performance 측정 코드는 그대로 사용할 수 있습니다. 준비된 변경분은 `/api/read`에서
전달될 수 있으므로 `/api/read-delta` 유무만으로 변경분 전송 여부를 판단하지 마세요.

추가 설명: [서버 사전 준비와 재접속 경로](../ko/prepared-reconnect.md).
